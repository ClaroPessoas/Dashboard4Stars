상세 분석

Step 1. 목적 및 범위

Page Agent는 알리바바가 공개한 MIT 라이선스 오픈소스 프로젝트로, 웹 페이지 내에 임베드되는 클라이언트 사이드 AI GUI 에이전트 라이브러리다. 핵심 차별점은 스크린샷·멀티모달 LLM·헤드리스 브라우저 없이 순수 텍스트 기반 DOM 조작만으로 동작한다는 점이다. browser-use(Python 기반 서버사이드 브라우저 자동화)에서 DOM 처리 컴포넌트와 프롬프트 패턴을 파생시켰으며, 이를 명시적으로 인정하고 원저작자 저작권을 보존하고 있다.

타겟 사용자: SaaS 제품 개발자(AI Copilot 삽입), 기업 ERP/CRM 자동화 팀, 접근성 도구 개발자, 브라우저 제어 에이전트 개발자.

Step 4. 아키텍처 분석

ReAct 에이전트 루프

execute(task)
  └─ while (step < maxSteps)
       ├─ observe(): getBrowserState() → FlatDomTree → simplified HTML
       ├─ think(): LLM.invoke(messages, MacroTool)
       │     └─ MacroTool: 모든 tool을 하나의 structured output으로 통합
       │           → evaluation_previous_goal | memory | next_goal | action
       └─ act(): tool.execute(input, { signal })

MacroTool 패턴이 핵심이다. 모든 에이전트 도구(click, input, scroll, wait, done 등)를 단일 Zod 스키마 공용체(z.union)로 패킹해, 매 스텝마다 LLM이 반드시 하나의 구조화된 도구를 호출하도록 강제한다. 이로써 파싱 실패·할루시네이션을 최소화한다.

이벤트 시스템

이벤트 영속성 목적
statuschange - 에이전트 상태 전환 (idle→running→completed/error/stopped)
historychange ✓ LLM 컨텍스트에 포함되는 영속 이력 변경
activity ✗ UI 전용 실시간 피드백 (thinking/executing/executed/retrying)
dispose - 에이전트 정리

DOM 파이프라인

browser-use 포크 기반 dom_tree/index.js가 라이브 DOM을 순회해 인터랙티브 요소를 인덱스 매핑([N]<type>text</type>) 형태의 simplified HTML로 변환한다. LLM은 스크린샷 없이 이 텍스트 표현만으로 요소를 선택하고, PageController가 인덱스를 통해 실제 DOM 요소를 찾아 조작한다.

계층 의존성

page-agent ──▶ core ──▶ llms
           ──▶ core ──▶ page-controller
           ──▶ ui
extension  ──▶ core, llms, page-controller, ui
mcp        ──▶ @modelcontextprotocol/sdk, ws

ui는 PanelAgentAdapter 인터페이스를 통해 PageAgentCore와 분리되어 있고, page-controller는 LLM 의존성이 전혀 없다. 순환 의존성 없음.

강점 (Strengths)

  1. 명확한 계층 분리와 역방향 의존성 없는 아키텍처: page-controller → llms → core → page-agent의 단방향 의존 그래프가 엄격하게 유지된다. 각 패키지는 독립적으로 테스트 가능하고, PageController는 LLM 없이 단독 사용 가능하다.

  2. MacroTool + Zod 스키마를 통한 구조화된 LLM 출력 강제: 모든 도구를 단일 공용체 스키마로 통합해 LLM이 매 스텝 반드시 정형화된 출력을 생성하도록 강제한다. 파싱 실패나 도구 선택 오류를 구조적으로 차단한다.

  3. AbortSignal 기반 협력적 취소 전파: 에이전트 루프, LLM 호출, 각 도구 실행, 라이프사이클 훅 모두가 단일 AbortController 신호를 공유하여 stop() 호출 시 즉각적이고 완전한 정리가 보장된다.

  4. 소스-퍼스트 모노레포로 내부 패키지 개발 경험 우수: 개발 중에는 src/*.ts를 직접 참조하므로 빌드 없이 즉시 변경이 반영된다. 퍼블리시 시에는 스크립트가 publishConfig를 자동 승격하므로 이중 관리 불필요.

  5. 활발한 릴리즈 사이클과 투명한 변경 이력: CHANGELOG가 breaking changes, features, improvements, bug fixes를 범주별로 명확히 기록하며, semver 규약을 준수한다. 주간 릴리즈 페이스가 유지된다.

위험 / 개선 필요 사항 (Risks & Areas for Improvement)

  1. 단독 메인테이너 리스크: 커밋 이력 기준 실질적 기여자가 1인이다. 버스 팩터(bus factor)가 1로, 핵심 기능 지식과 릴리즈 권한이 집중되어 있다. 알리바바 조직 이름으로 운영되나 다중 메인테이너 체계는 아직 구축되지 않은 것으로 보인다.

  2. 클라이언트 사이드 API 키 노출: BYOK 아키텍처에서 apiKey가 브라우저 번들에 포함되는 구조다. 서버사이드 프록시 없이 직접 사용 시 키 노출 위험이 상존한다. 문서가 경고는 하나 구조적 보호 수단이 없다.

  3. E2E 테스트 부재와 부분적 단위 테스트 커버리지: @page-agent/llms 외 패키지의 테스트는 초기 단계이다. 에이전트 루프 전체를 실제 브라우저 환경에서 검증하는 E2E 테스트가 없어 회귀 탐지 능력이 제한적이다.

  4. TypeScript 6 beta 의존성: typescript: ^6.0.3은 아직 정식 릴리즈 전 버전이다. 다운스트림 사용자의 TypeScript 버전 호환성 문제나 예기치 않은 API 변경 가능성이 있다.

  5. DOM tree engine의 JavaScript 사용과 browser-use 포크 유지 부담: page-controller/src/dom/dom_tree/index.js가 TypeScript가 아닌 JavaScript로 작성되어 타입 안전성이 없다. 또한 browser-use의 특정 커밋(0.5.9 d51b6e73)에서 포크된 코드로, 업스트림 버그 픽스나 개선을 수동으로 추적·병합해야 하는 유지보수 부담이 있다.

도입 권고 (Adoption Recommendation)

기술 도입 관점: 웹 애플리케이션에 AI Copilot 기능을 빠르게 추가하려는 팀에게 강력히 권장한다. 백엔드 재작성 없이 클라이언트 사이드 JS 몇 줄로 통합 가능하고, OpenAI 호환 API라면 어떤 LLM이든 사용할 수 있는 BYOK 모델이 채택 장벽을 낮춘다.

아키텍처 벤치마킹 관점: MacroTool 패턴, 이벤트-분리형 UI, 인덱스 기반 DOM 조작 파이프라인은 브라우저 에이전트 설계의 실용적 참조 구현으로 가치가 높다.

프로덕션 채택 시 주의사항: - API 키를 서버사이드 프록시로 격리할 것 - @page-agent/core를 직접 사용하면 UI 없이 더 유연하게 통합 가능 - TypeScript 6이 정식 릴리즈될 때까지 TS 버전 호환성을 모니터링할 것 - 단독 메인테이너 구조이므로 포크 전략을 고려하거나 업스트림 기여를 통해 지식 분산을 유도할 것

보안 검토 관점: 클라이언트 사이드 전용 구조로 서버 공격 표면이 없고, SECURITY.md와 Dependabot이 기본 위생을 갖추고 있다. 다만 SBOM과 아티팩트 서명이 없으므로 엄격한 공급망 보안 요구 환경에서는 보완이 필요하다.

기여 준비도: AGENTS.md, developer-guide, CONTRIBUTING.md가 잘 정비되어 있고 commitlint + ESLint strict로 코드 품질 기준이 자동화되어 있어 신규 기여자 온보딩 환경이 양호하다. AI 코딩 정책(코어 코드에 vibe coding 금지)이 명시적으로 문서화된 점이 특히 인상적이다.
