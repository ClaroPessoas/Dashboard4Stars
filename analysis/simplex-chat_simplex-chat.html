Step 1. 목적과 범위

SimpleX Chat은 사용자 식별자가 전혀 없는 최초의 메시징 플랫폼을 표방한다. 기존 메신저들이 전화번호·이메일·사용자 ID 등 영구 식별자를 사용하는 것과 달리, SimpleX는 연결마다 일회성 메시지 큐 주소(SMP Queue)를 할당해 메타데이터 노출을 최소화한다.

해결하는 문제: 누가 누구와 대화하는지(통신 메타데이터) 보호, 중앙화 서버 의존 제거, 소셜 그래프 노출 방지.

분류: 오픈소스 P2P/연합 메시징 플랫폼 (클라이언트 앱 + 프로토콜 + 서버 인프라)

Step 2. 저장소 구조 분석

모노레포 구조로 6개 플랫폼 코드가 한 저장소에 집중:

simplex-chat/
├── src/Simplex/Chat/         # Haskell 코어 (252 .hs 파일)
├── apps/
│   ├── multiplatform/         # Kotlin Compose KMP (335 .kt 파일)
│   ├── ios/                   # SwiftUI iOS (217 .swift 파일)
│   ├── simplex-chat/          # CLI 진입점
│   └── simplex-bot*/          # 봇 프레임워크들
├── packages/
│   ├── simplex-chat-nodejs/   # Node.js 네이티브 애드온 SDK
│   └── simplex-chat-python/   # Python SDK
├── tests/                     # Haskell 테스트
├── docs/                      # 프로토콜 사양, RFC, 가이드
├── plans/                     # 설계·구현 계획 50개 이상 공개
└── flake.nix / Dockerfile     # 재현 빌드

구조는 도메인 지향 (Store/Direct, Store/Groups, Store/Files 등).

Step 3. 소프트웨어 스택

계층 기술
백엔드 Haskell GHC 9.6.3, Cabal 3.10
암호화 crypton 0.34, Double ratchet, X25519, Ed25519, TLS 1.3
데이터베이스 SQLite + SQLCipher (AES-256), PostgreSQL 옵션
모바일/데스크톱 Kotlin Multiplatform + Compose, SwiftUI
봇 SDK Node.js (native addon), Python
인프라 Docker, GitHub Actions, Nix flake
코드 품질 fourmolu (Haskell), GHC -Weverything

Step 4. 아키텍처

[iOS/Android/Desktop/CLI/Node.js]
         ↓ C FFI (JSON-over-FFI)
[Haskell Core: Controller → Commands → Store/SQLCipher]
         ↓ simplexmq Agent
[SMP Relay Servers (자체 또는 운영자)]
  • Haskell 코어: ReaderT/ExceptT 모나드 스택 기반 레이어드 아키텍처. STM 동시성.
  • 모바일 프론트엔드: MVI 패턴, ChatModel.kt 전역 상태, Compose StateFlow.
  • FFI 브리지: chatMigrateInit / chatSendCmd / chatRecvMsg C 익스포트.

강점 (Strengths)

  1. 독창적인 프라이버시 아키텍처 — 사용자 식별자 완전 제거라는 근본적으로 다른 접근법이 프로토콜부터 UX까지 일관되게 관통
  2. 효율적인 멀티 플랫폼 FFI 아키텍처 — Haskell 코어 하나로 6개 플랫폼(Android/Desktop/iOS/CLI/Node.js/Python) 지원, 비즈니스 로직 중복 없음
  3. 강력한 공급망 보안 — 핵심 암호화·DB 의존성 자체 포크 관리, git hash 고정, Nix flake 재현 빌드, 일일 CI 검증
  4. 전문적인 외부 감사 — Trail of Bits 2회 독립 감사, 보고서 전문 공개
  5. 활발한 개발과 투명한 계획 공개 — 50개 이상 설계 문서 공개, 3~4개월 메이저 릴리스 사이클

위험/개선 필요 사항 (Risks)

  1. Haskell 생태계 진입 장벽 — 기여자 풀 극소수, 핵심팀 의존도 과도
  2. JSON-over-FFI 브리지의 성능·타입 안전성 한계 — 런타임 타입 오류 위험, 성능 오버헤드
  3. 테스트 커버리지 정량화 미비 — cabal coverage 옵션 주석 처리, CI 통합 없음
  4. 공식 SBOM 파일 부재 — 기업 도입 및 공급망 감사 시 표준화된 SBOM 필요
  5. 복잡한 크로스 플랫폼 빌드 환경 — GHC + Cabal + Gradle + Xcode + Nix 혼재, 로컬 개발 환경 설정 복잡

도입 권고 (Recommendation)

강력 권고 시나리오: - 의료기관·법률사무소·언론사 등 메타데이터 보호가 필수인 조직 내부 통신 - 자체 SMP 서버 운영으로 완전 자율 통신 인프라를 원하는 조직 - LLM 통합, 고객지원 봇 등 Node.js/Python SDK 기반 자동화

주의사항: AGPL-3.0 라이선스로 네트워크 서비스에 수정 버전 사용 시 소스 공개 의무 발생. Haskell 코어 기여는 높은 기술 수준 요구 (팀 사전 협의 필수).
