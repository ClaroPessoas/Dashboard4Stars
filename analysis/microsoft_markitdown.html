상세 분석

Step 1. 목적 및 범위

MarkItDown은 LLM 텍스트 분석 파이프라인을 위한 파일→Markdown 변환 유틸리티다. README의 핵심 철학은 명확하다: 주류 LLM은 Markdown을 native하게 이해하며, Markdown은 문서 구조(제목·목록·표·링크)를 유지하면서도 토큰 효율이 높다. 유사 도구인 textract와 달리, 사람이 읽는 고품질 변환보다 AI 소비 최적화에 집중한다.

대상 사용자: LLM 애플리케이션 개발자, RAG 파이프라인 구축자, 문서 분석 자동화 엔지니어.

지원 포맷 (20+ 종): - 문서: PDF, DOCX, PPTX, XLSX, XLS, EPUB, MSG (Outlook) - 웹: HTML, RSS, Wikipedia, Bing SERP, YouTube (자막) - 미디어: 이미지(EXIF+LLM), 오디오(EXIF+STT) - 구조: CSV, JSON, XML, ZIP (재귀) - 코드: Jupyter Notebook (.ipynb) - 클라우드: Azure Document Intelligence, Azure Content Understanding

Step 4. 아키텍처 분석

핵심 패턴: 우선순위 기반 Chain of Responsibility

MarkItDown.convert(source)
  └─ convert_local() / convert_uri() / convert_stream() / convert_response()
       └─ _get_stream_info_guesses()    # magika + charset-normalizer로 StreamInfo 확충
            └─ _convert(stream_info_guesses=[...])
                 └─ sorted(converters, key=priority)
                      ├─ converter.accepts(stream, info) → bool
                      └─ converter.convert(stream, info) → DocumentConverterResult

우선순위 체계: - PRIORITY_SPECIFIC_FILE_FORMAT = 0.0 (기본, 포맷 특화 컨버터) - PRIORITY_GENERIC_FILE_FORMAT = 10.0 (catch-all: PlainText, HTML, Zip) - OCR 플러그인: -1.0 (내장보다 먼저 시도) - 낮은 값 = 높은 우선순위

플러그인 시스템:

[project.entry-points."markitdown.plugin"]
ocr = "markitdown_ocr"

importlib.metadata.entry_points()로 lazy 로드. register_converters(markitdown, **kwargs) 인터페이스.

StreamInfo (frozen dataclass): mimetype, extension, charset, filename, local_path, url — 불변 값 객체, copy_and_update()로 체인 전파.

모듈 경계: - _markitdown.py: 오케스트레이터, 컨버터 레지스트리, URI 라우팅 - converters/: 각 포맷별 단일 파일 컨버터 (총 4,695줄, 20개+ 파일) - converter_utils/docx/math/: OMML→LaTeX 변환 (dwml 기반)

아키텍처 패턴 평가: - 플러그인 우선 개방/폐쇄 원칙 준수 ✓ - 순수 함수형 스트림 처리, 부작용 없음 ✓ - LLM 클라이언트 의존성은 kwargs 주입, 직접 결합 없음 ✓ - **kwargs 남용으로 타입 안전성 부분 희생 (TODO 주석 존재)

강점

  1. 명확한 단일 책임 원칙: "모든 것을 Markdown으로" — 범위가 명확하고 목적이 일관됨. LLM 파이프라인의 전처리 단계로서 독보적 포지셔닝.

  2. 확장 가능한 플러그인 아키텍처: entry_points + 우선순위 레지스트리 조합으로 코어 코드 수정 없이 새 포맷 추가 가능. OCR 플러그인이 이를 실증.

  3. 보안 인식 설계: defusedxml 강제 사용, ExifTool CVE 버전 검증, JavaScript URL 필터링, rlink 공격 방어 등 실제 취약점을 코드 레벨에서 명시적으로 대응.

  4. 무상태 스트림 처리: 영구 저장소 없이 순수 BinaryIO 기반 처리. 서버리스·컨테이너 환경에 자연스럽게 적합.

  5. MCP 프로토콜 지원: LLM 에이전트와의 통합을 위한 MCP 서버 패키지 포함. AI 에이전트 생태계와의 연결성이 우수.

위험 / 개선 필요 사항

  1. Python 의존성 자동 취약점 스캔 부재: dependabot이 GitHub Actions만 모니터링. pdfminer, mammoth, magika 등 핵심 의존성의 CVE는 수동 점검에 의존. pip-audit 또는 safety를 CI에 추가해야 함.

  2. 커버리지 측정 미통합: pyproject.toml에 coverage 설정은 있으나 CI에서 측정·리포트하지 않음. 복잡한 컨버터 분기 코드의 테스트 사각지대 파악 불가.

  3. **kwargs 타입 희석: MarkItDown.__init__() 및 모든 컨버터가 **kwargs를 통해 옵션을 전달. 런타임까지 타입 오류 미발견, IDE 지원 부족. TODO 주석도 인지하고 있으나 미해결.

  4. MCP 서버 인증 부재: markitdown-mcp는 인증 메커니즘이 전혀 없음. HTTP 모드에서 비localhost 바인딩 시 경고만 출력. 프로덕션 배포 시 보안 프록시 없이는 위험.

  5. CONTRIBUTING.md 및 CHANGELOG 부재: 신규 기여자 온보딩이 README 내 짧은 섹션에 의존. 버전별 변경 이력이 GitHub Release/PR에만 분산되어 있어 도입 결정 시 변경 이력 추적이 어려움.

Core components and their roles:

Component Role
MarkItDown class Central routing engine. Opens input as a stream, detects MIME type, delegates to appropriate converter
DocumentConverter (abstract) Base class for all converters. Defines accepts() + convert() interface
StreamInfo Immutable dataclass carrying file metadata (MIME, extension, charset, URL, etc.) through the pipeline
Individual converters Handle specific formats (PdfConverter, DocxConverter, etc. — 20+ total)
magika library Google's ML-based file type detector — infers MIME type from content even without extension
Plugin system Dynamically injects third-party converters via Python entry points
markitdown-mcp MCP server implemented with FastMCP — supports STDIO or HTTP/SSE transport

Data flow: 1. User calls md.convert(source) (accepts file path, URL, Path, BinaryIO, or requests.Response) 2. 6. 성능 및 확장성 고려사항 / Performance & Scalability

[한국어]

알려진 성능 병목 지점:

  1. 대용량 PDF 처리: pdfminer.six + pdfplumber 기반 PDF 파싱은 페이지가 많거나 복잡한 레이아웃의 경우 메모리/시간 소모가 클 수 있습니다. 100페이지 이상의 PDF는 Azure Document Intelligence 사용을 권장합니다.
  2. 이미지 기반(스캔) PDF: OCR 없이 처리 불가 — markitdown-ocr 플러그인 또는 Azure 서비스가 반드시 필요합니다.
  3. LLM API 호출 지연: llm_client를 설정하면 PPTX의 각 이미지마다 API 호출이 발생하므로 슬라이드 수에 비례해 처리 시간이 늘어납니다.
  4. magika 초기화: MarkItDown() 인스턴스 생성 시 magika ML 모델이 로드됩니다. 고처리량 환경에서는 인스턴스를 재사용하세요 (요청마다 새 인스턴스를 만들지 마세요).

수평/수직 확장 전략:

# 올바른 패턴: 인스턴스 재사용 (module-level singleton)
_md_instance = MarkItDown()

def convert_file(path: str) -> str:
    return _md_instance.convert(path).markdown

# 잘못된 패턴: 요청마다 새 인스턴스 생성 (magika 재로드 발생)
def convert_file_bad(path: str) -> str:
    return MarkItDown().convert(path).markdown  # 비효율적!
  • 수평 확장: MarkItDown은 스테이트리스(상태 없음)이므로 워커 프로세스(Celery, multiprocessing.Pool 등)를 여러 개 띄워 병렬 처리 가능합니다.
  • 배치 처리: 대량 파일 처리 시 concurrent.futures.ThreadPoolExecutor 또는 ProcessPoolExecutor 활용을 권장합니다.
  • 메모리 관리: convert_stream()을 사용하면 전체 파일을 메모리에 로드하지 않고 스트림으로 처리 가능합니다.

캐싱 전략: - MarkItDown 자체에는 캐싱 기능이 없습니다. 동일 파일을 반복 변환하는 경우, 상위 레이어에서 파일 해시(MD5/SHA256) 기반 결과 캐싱을 구현하세요.

모니터링: - result.markdown의 길이(토큰 수)를 추적하여 변환 품질 모니터링 가능 - Azure 서비스 사용 시 Azure Monitor로 API 호출량 및 비용 추적 - FileConversionException, UnsupportedFormatException을 로깅하여 실패율 모니터링

[English]

Known performance bottlenecks:

  1. Large PDF processing: The pdfminer.six + pdfplumber PDF parser can be slow and memory-intensive for documents with many pages or complex layouts. Azure Document Intelligence is recommended for 100+ page PDFs.
  2. Image-based (scanned) PDFs: Cannot be processed without OCR — the markitdown-ocr plugin or an Azure service is required.
  3. LLM API call latency: When llm_client is configured, each image in a PPTX triggers an API call, so processing time scales linearly with slide count.
  4. magika initialization: Creating a MarkItDown() instance loads the magika ML model. In high-throughput environments, reuse the instance — do not create a new one per request.

Horizontal / vertical scaling strategies:

# Correct pattern: reuse instance (module-level singleton)
_md_instance = MarkItDown()

def convert_file(path: str) -> str:
    return _md_instance.convert(path).markdown

# Wrong pattern: new instance per request (reloads magika every time)
def convert_file_bad(path: str) -> str:
    return MarkItDown().convert(path).markdown  # inefficient!
  • Horizontal scaling: MarkItDown is stateless, so multiple worker processes (Celery, multiprocessing.Pool, etc.) can run in parallel without conflict.
  • Batch processing: Use concurrent.futures.ThreadPoolExecutor or ProcessPoolExecutor for bulk file conversion.
  • Memory management: convert_stream() allows processing without loading the entire file into memory at once.

Caching strategy: - MarkItDown has no built-in caching. For repeated conversion of the same files, implement hash-based (MD5/SHA256) result caching at the application layer.

Monitoring: - Track len(result.markdown) (or token count) as a proxy for conversion quality - When using Azure services, use Azure Monitor to track API call volume and cost - Log FileConversionException and UnsupportedFormatException to monitor conversion failure rates
