1. 목적과 범위 (Purpose & Scope)

Hermes Agent는 Nous Research가 개발한 자기 개선형 AI 에이전트로, "경험에서 스킬 생성 → 사용 중 개선 → 크로스세션 기억 유지"라는 학습 루프가 핵심 차별점이다. 사용자가 직접 $5 VPS, GPU 클러스터, 또는 Modal·Daytona 서버리스 환경 어디서나 실행할 수 있도록 설계됐다.

대상 사용자: - 개인 개발자 (로컬 터미널 에이전트) - 연구자 (배치 트라젝토리 생성, 훈련 데이터 수집) - 팀·조직 (메시징 게이트웨이, 자동화 스케줄러) - AI 앱 빌더 (ACP 에디터 통합, MCP 서버 모드)

카테고리: 오픈소스 AI 에이전트 프레임워크 겸 개인 비서 플랫폼

1. 프로젝트 개요 / Project Overview

1.1 목적 및 분류 / Purpose and Classification

  • 해결하는 문제 / Problem solved: 다양한 LLM 프로바이더를 지원하고, 경험으로부터 스킬을 자가 생성·개선하는 자기 발전형(self-improving) AI 에이전트. 터미널(TUI), 메시징 플랫폼(Telegram, Discord, Slack, WhatsApp, Signal, Matrix, WeChat, DingTalk, Feishu 등), OpenAI 호환 API 서버까지 단일 에이전트 프로세스로 통합 제공. 크론 스케줄러, 서브에이전트 병렬 위임, 배치 궤적 생성(학습 데이터 생성) 기능 포함.

영문 요약 / English Summary: Hermes Agent is a self-improving AI agent built by Nous Research that features a closed learning loop (autonomous skill creation, skill self-improvement, persistent memory, cross-session recall). It supports 10+ LLM providers via an OpenAI-compatible interface, integrates with 15+ messaging platforms, includes a built-in cron scheduler, and can delegate to parallel sub-agents. The platform targets both personal use (desktop, VPS) and cloud/serverless deployment (Modal, Daytona, Docker, Singularity).

6. 성능 및 확장성 고려사항 / Performance & Scalability

[한국어]

알려진 성능 병목 지점:

  1. 컨텍스트 압축 지연: 세션이 길어지면 자동 압축 트리거 시 추가 LLM 호출 발생. 임계값 조정: yaml # ~/.hermes/config.yaml compression: enabled: true threshold: 0.85 # 85%에서 압축 (기본값) summary_model: "google/gemini-3-flash-preview" # 경량 모델 사용

  2. 터미널 백엔드 스핀업 시간: Modal/Daytona 백엔드는 콜드 스타트 ~2–10초. 빈번한 단기 명령에는 local 백엔드 사용.

  3. 도구 레지스트리 초기화: 에이전트 시작 시 모든 tools/*.py를 임포트. 불필요한 도구셋 비활성화: bash hermes tools # 도구셋별 활성화/비활성화

  4. 스킬 시스템 프롬프트 크기: 스킬이 많을수록 시스템 프롬프트 증가 → 토큰 비용 상승. 조건부 스킬 활성화(requires_toolsets, fallback_for_toolsets) 활용.

수평/수직 확장 전략: - 수직 확장: 단일 인스턴스는 메모리/CPU 추가로 확장. SQLite는 단일 프로세스 최적화. - 수평 확장: 각 사용자/플랫폼을 독립 컨테이너로 분리 (HERMES_HOME 다르게 설정). 게이트웨이 Webhook 모드 사용 (폴링 대신). - 다중 에이전트 위임: delegate_tool로 병렬 서브에이전트 생성 — 독립 작업 병렬화에 효과적.

캐싱 전략: - 스킬 인덱스는 ~/.hermes/skills/ 변경 시만 재빌드 - 세션 검색은 SQLite FTS5 인덱스 활용 (빠른 전문 검색) - LLM 응답 캐싱은 내장 미지원 — 프록시 레이어(OpenRouter 캐싱 기능 활용) 고려

Known performance bottlenecks:

  1. Context compression latency: Long sessions trigger auto-compression (an extra LLM call). Tune the threshold: yaml # ~/.hermes/config.yaml compression: enabled: true threshold: 0.85 # compress at 85% (default) summary_model: "google/gemini-3-flash-preview" # use a lightweight model

  2. Terminal backend cold-start time: Modal/Daytona backends have ~2–10s cold start. For frequent short commands, use the local backend.

  3. Tool registry initialization: All tools/*.py are imported at agent startup. Disable unused toolsets: bash hermes tools # enable/disable toolsets interactively

  4. Skills system prompt size: More active skills = larger system prompt = higher token cost. Use conditional skill activation (requires_toolsets, fallback_for_toolsets) to keep prompts lean.

Horizontal / vertical scaling strategies: - Vertical scaling: Single instance scales with more RAM/CPU. SQLite is optimized for single-process use. - Horizontal scaling: Isolate each user/platform in its own container (different HERMES_HOME). Use Webhook mode for the gateway instead of polling. - Multi-agent delegation: Use delegate_tool to spawn parallel subagents — effective for independent parallel workstreams.

Caching strategy: - Skill index is only rebuilt when ~/.hermes/skills/ changes - Session search uses SQLite FTS5 index for fast full-text queries - LLM response caching is not built in — consider a proxy layer (e.g., OpenRouter's caching features)

Monitoring and logging:

tail -f ~/.hermes/sessions/*.jsonl     # gateway session logs

# Diagnostics
hermes doctor                           # full environment health check

# Docker
docker logs -f hermes                   # container logs

Session logs are auto-saved as logs/session_YYYYMMDD_HHMMSS_UUID.json.

7. 보안 체크리스트 / Security Checklist

[한국어]

환경 변수 및 시크릿 관리: - [ ] API 키는 ~/.hermes/.env에 저장 (소스 코드 또는 config.yaml에 직접 넣지 말 것) - [ ] Docker 배포 시 Secrets Manager 또는 환경 변수로 주입 (이미지에 하드코딩 금지) - [ ] SSH 원격 백엔드 사용 시 에이전트가 .env 파일에 접근 불가 (보안 권장) - [ ] 로그에 API 키/토큰/비밀번호가 노출되지 않는지 주기적 확인

인증/인가 구현 포인트: - 메시징 게이트웨이: TELEGRAM_ALLOWED_USERS, DISCORD_ALLOWED_USERS, SLACK_BOT_TOKEN 등으로 허용 사용자 명시 - GATEWAY_ALLOW_ALL_USERS=false (기본값 유지 — 의도적인 공개 접근이 아닌 한 변경 금지) - Docker exec 시 특권 드롭: /opt/hermes/bin/hermes exec shim이 root로 실행 시 자동 s6-setuidgid hermes - 위험 명령 실행 전 사용자 승인: tools/approval.py의 패턴 매칭 + 세션별 승인 흐름

Environment variable and secret management: - [ ] API keys stored in ~/.hermes/.env only (never hardcode in source code or config.yaml) - [ ] For Docker deployments, inject via Secrets Manager or environment variables (never bake into the image) - [ ] When using the SSH remote backend, the agent cannot access the local .env file (recommended for security) - [ ] Periodically audit logs to ensure no API keys/tokens/passwords appear in output

Authentication / authorization implementation points: - Messaging gateway: specify allowed users via TELEGRAM_ALLOWED_USERS, DISCORD_ALLOWED_USERS, SLACK_BOT_TOKEN, etc. - Keep GATEWAY_ALLOW_ALL_USERS=false (the default) unless intentionally enabling public access - Docker exec privilege drop: /opt/hermes/bin/hermes exec shim auto-drops to s6-setuidgid hermes when invoked as root - Dangerous command approval before execution: tools/approval.py pattern matching + per-session approval flow

Dependency vulnerability scanning:

# OSV scanner (runs automatically in CI)
osv-scanner --lockfile uv.lock

# Ruff lint (checks supply-chain-related coding patterns)

# Windows safety pattern checker
python scripts/check-windows-footguns.py

Known security considerations: - Shell injection: Dangerous command detection in tools/approval.py + shlex.quote() for sudo password piping - Path traversal: Write deny list (~/.ssh/authorized_keys, /etc/shadow) resolved via os.path.realpath() to prevent symlink bypass - Prompt injection: Cron prompt injection scanner in tools/cronjob_tools.py - Skill security: tools/skills_guard.py scans hub-installed skills for malicious patterns - Code execution sandbox: execute_code child process strips API key env vars from its environment - Container hardening: Docker drops all capabilities, no privilege escalation, PID limits, size-limited tmpfs - Supply chain: All PyPI dependencies are exact-pinned with <next_major upper bound (policy after 2026 supply-chain attacks)
