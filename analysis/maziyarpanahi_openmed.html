Step 1. 목적 및 범위 정의

프로젝트가 해결하는 문제

OpenMed는 의료 데이터의 클라우드 유출 없이 생물의학 NLP를 수행할 수 있는 로컬 우선(local-first) AI 플랫폼이다. 기존 의료 AI 솔루션의 세 가지 주요 문제를 동시에 해결한다:

  1. 데이터 프라이버시: 환자 PHI(Protected Health Information)가 외부 서버로 전송되는 클라우드 API 의존성 제거
  2. 도메인 접근성: 1,000개 이상의 HuggingFace 생물의학 모델을 한 줄의 Python 코드로 사용 가능하게 통합
  3. HIPAA 규정 준수: 247개의 PII 체크포인트, 12개 언어 지원으로 HIPAA Safe Harbor 기준에 부합하는 비식별화 자동화

대상 사용자

사용자 그룹 사용 시나리오
임상 NLP 연구자 의료 텍스트 개체명 인식(NER), 임상 기록 분석
HIPAA 준수가 필요한 의료 스타트업 환자 기록 비식별화, 임상 데이터 파이프라인
Apple 생태계 개발자 iOS/macOS 의료 앱 내 온디바이스 NLP (OpenMedKit)
DevSecOps / 데이터 엔지니어 REST API, Docker, 배치 파이프라인으로 EMR 시스템 통합

프로젝트 유형

플랫폼 + 라이브러리 + SDK의 복합 구조: - openmed — Python 라이브러리/프레임워크 (PyPI 배포) - openmed.service — 독립 실행 REST API 서비스 - OpenMedKit — Swift 패키지 (네이티브 iOS/macOS SDK) - 문서 사이트 (GitHub Pages + MkDocs)

레이어 분리

레이어 모듈 역할
프레젠테이션 service/app.py, service/schemas.py HTTP 요청/응답 직렬화, API 계약
비즈니스 로직 core/pii.py, core/anonymizer/, processing/advanced_ner.py PII 추출, 비식별화, NER 집계
데이터 접근 core/models.py, core/model_registry.py, mlx/ 모델 로드, 추론 실행, 레지스트리 쿼리
인프라 core/backends.py, core/config.py, utils/ 백엔드 라우팅, 설정, 로깅

아키텍처 패턴

  • 레이어드 아키텍처(Layered Architecture): 프레젠테이션 → 비즈니스 → 데이터 계층 명확히 분리
  • 전략 패턴(Strategy Pattern): backends.py가 HF/MLX 추론 전략을 런타임에 선택
  • 레지스트리 패턴(Registry Pattern): model_registry.py + models.jsonl로 1,000+ 모델 메타데이터 중앙 관리
  • 파이프라인 패턴(Pipeline Pattern): processing/ 내 처리 단계의 순차적 체인
  • Facade 패턴: openmed/__init__.py가 복잡한 내부 구조를 단순한 공개 API로 노출

상태 관리

  • 무상태(Stateless) HTTP 레이어: FastAPI 서비스는 요청 간 상태 보관 없음
  • 인메모리 모델 캐시: ModelLoader가 로드된 파이프라인을 프로세스 메모리에 캐시
  • XDG 설정 파일: ~/.config/openmed/ 에 YAML/TOML 형식으로 사용자 설정 영속화
  • 모델 레지스트리: models.jsonl에 정적 메타데이터로 매니페스트 관리

강점 (Strengths)

  1. 프라이버시 우선 아키텍처 (Privacy-First Architecture) 온디바이스 처리 원칙이 아키텍처 모든 레이어에 일관되게 구현됨. 환자 데이터가 네트워크 경계를 벗어나지 않는다는 것이 코드 수준에서 검증 가능하며, HIPAA Safe Harbor 요건을 충족하는 PII 처리 파이프라인이 완성됨.

  2. 선택적 의존성(Extras) 설계의 우수성 pip install "openmed[hf,service]" 형태의 extras 구조로 클라이언트가 필요한 런타임만 설치 가능. CPU/GPU/MLX/CoreML 환경에 맞게 풋프린트를 최소화할 수 있으며, 이는 의료 엣지 디바이스 배포 시 특히 유리함.

  3. 멀티플랫폼 CI/CD 성숙도 Ubuntu/Windows/macOS × Python 3.10-3.12의 9개 조합과 Apple Silicon 전용 워크플로, Swift 빌드까지 포함하는 포괄적인 CI 매트릭스. 크로스플랫폼 의료 소프트웨어에서 흔히 놓치는 플랫폼 회귀를 조기 발견 가능.

  4. 도메인 특화 처리 엔진의 깊이 pii_entity_merger.py의 날짜/전화번호 패턴 인식 기반 단편화 방지, tokenization.py의 임상 용어 경계 보존, pii_i18n.py의 12개 언어 레이블 매핑 등 의료 NLP 도메인에 특화된 처리 로직이 체계적으로 구현됨.

  5. 즉시 사용 가능한 문서와 예제 24개 이상의 MkDocs 가이드, 5개 이상의 실행 가능한 예제 스크립트, 13개 언어 README, Streamlit 웹 데모까지 포함. 온보딩 장벽이 극히 낮아 도입 결정에서 PoC까지의 사이클이 수 시간 이내 가능.

위험/개선 필요 사항 (Risks & Improvement Areas)

  1. 단일 기여자(버스 팩터) 위험 주요 커밋과 릴리스가 maziyarpanahi 단일 계정에 집중된 것으로 보임. 프로덕션 헬스케어 시스템에 도입 시, 메인테이너 부재가 보안 패치나 규정 변경 대응 지연으로 이어질 수 있음. 코어 기여자 2인 이상 확보 및 GitHub Org 이전을 권고.

  2. SECURITY.md, SBOM, 아티팩트 서명 부재 SECURITY.md 미확인(보안 취약점 신고 채널 불명확), SBOM(소프트웨어 자재 명세서) 미생성, PyPI 배포 아티팩트 서명(Sigstore/cosign) 미적용. HIPAA/HITECH 규정의 소프트웨어 공급망 보안 요건 강화 추세를 고려하면 조기 개선 필요.

  3. 거대 단일 파일 (God File) 문제 core/pii_i18n.py(~58K LOC), mlx/inference.py(~43.7K LOC), processing/batch.py(~23.8K LOC)가 각각 단일 파일에 집중됨. 이는 코드 리뷰, 테스트 격리, 기여자 온보딩을 어렵게 하며, 언어별/기능별 모듈 분리 리팩토링이 권고됨.

  4. Dependabot/Renovate 자동화 부재 가능성 safety CI 스캔은 존재하나, PR 기반 의존성 자동 업데이트(Dependabot/Renovate) 설정이 확인되지 않음. 의료 소프트웨어에서 CVE 대응 SLA 준수를 위해 자동 의존성 업데이트 PR 파이프라인 구성이 필요.

  5. REST 서비스 인증/인가 미확인 openmed/service/app.py의 FastAPI 엔드포인트에 인증 미들웨어(JWT, API Key, OAuth2) 구현 여부가 확인되지 않음. 내부망 배포 전제일 수 있으나, Docker 이미지 공개 노출 시 환자 데이터 처리 엔드포인트가 인증 없이 접근 가능할 위험이 있음. 배포 아키텍처에 인증 레이어 명시 권고.

운영 성숙도 종합 판단

OpenMed는 의료 AI 영역에서 드물게 발견되는 프라이버시 우선 + 멀티플랫폼 + 즉시 사용 가능한 성숙도를 갖춘 프로젝트다. Apache-2.0 라이선스로 상업적 도입 장벽이 없으며, 적극적인 릴리스 주기와 포괄적인 문서가 낮은 온보딩 비용을 보장한다. 단, 헬스케어 프로덕션 환경에서는 공급망 보안 강화와 REST 서비스 인증 레이어 검증이 도입 선결 조건이다.
