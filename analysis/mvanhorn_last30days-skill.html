1. 프로젝트 개요 / Project Overview

1.1 목적 및 분류 / Purpose and Classification

해결하는 문제 / Problem solved: Reddit, X(Twitter), YouTube, TikTok, Instagram, Hacker News, Polymarket, GitHub 등 15개 이상의 소셜·뉴스 소스에서 최근 30일간의 실제 참여 데이터(좋아요·업보트·배팅금 가중치)를 수집·집계하여, Claude Code 등 AI 에이전트 하네스에서 /last30days <주제> 슬래시 커맨드로 즉시 사용할 수 있는 리서치 자동화 도구를 제공한다.

기존 Google 검색 기반 도구가 SEO 편향 결과를 반환하는 반면, 이 스킬은 실제 사람들이 실제로 반응한 콘텐츠를 참여도 가중 스코어링(관련성 45% + 최신성 25% + 참여도 30%)으로 순위화한다.

3.2 알려진 위험 요소 / Known Risk Factors

의존성 취약점: - 프로덕션 의존성 0개 → 직접 의존성 CVE 위험 최소화 - Dev 의존성(pytest, pytest-cov)은 프로덕션 빌드에 미포함

쿠키 기반 인증 취약점: chrome_cookies.py, cookie_extract.py, safari_cookies.py 모듈이 브라우저 쿠키를 추출하여 X, TikTok, Instagram 인증에 사용. 이 접근 방식은: - 브라우저 업데이트에 취약(brittle) - 사용자 세션 토큰이 로컬 파일에 접근 가능한 상태로 존재 - 일부 플랫폼의 ToS 위반 소지

하드코딩된 시크릿: env.py 파일이 25.9 KB로 대형이며 다수의 API 키 환경변수를 처리. TruffleHog 스캔이 적용되어 있으나 --only-verified 플래그로 false positive를 줄이는 대신 일부 실제 시크릿을 놓칠 수 있음. 실제 시크릿 커밋 여부는 직접 확인 불가이나, TruffleHog 스캔 존재 자체가 방어 의도를 시사.

continue-on-error: true 보안 워크플로우: 현재 보안 스캔이 PR 머지를 차단하지 않는다. 취약점/시크릿 발견 시에도 배포가 진행될 수 있음.

Known performance characteristics:

Characteristic Description
Parallel fanout lib/fanout.py runs per-source searches in parallel → total run time = slowest source response
Zero external dependencies stdlib only → minimal import overhead
Network-bound Real bottleneck is external API response times (Reddit, X API, YouTube, etc.)
SQLite persistence --store flag persists results to local SQLite → can reduce cost of repeated queries

Bottleneck mitigation strategies:

  1. Exclude slow sources: Use --search=reddit,hn to select fast sources only, or set EXCLUDE_SOURCES to exclude slow ones
  2. Adjust timeouts: The urllib wrapper in lib/http.py controls retry/timeout behavior
  3. --emit=compact: Reduces output size vs. the default full markdown output
  4. Cache with SQLite: --store flag persists results so repeated queries don't re-fetch

Horizontal/vertical scaling:

  • Vertical scaling: Python GIL limits multi-core utilization. Optimizing network latency (source selection, timeouts) yields more than adding CPU/RAM
  • Horizontal scaling: Running multiple independent instances with topic partitioning is the most practical approach (each instance is stateless)
  • Cron-based pre-aggregation: Pre-running topics on a schedule and reading from SQLite is faster than on-demand fetching for known recurring topics
