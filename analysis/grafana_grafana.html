상세 분석 (Detailed Analysis)

1. 목적 및 범위

Grafana는 "어디에 있든 메트릭을 쿼리·시각화·알림하는 플랫폼"이라는 단일 미션 하에, 운영팀·SRE·데이터엔지니어를 주요 사용자로 삼는 플랫폼형 오픈소스 애플리케이션이다. 단순 라이브러리가 아닌, 플러그인 생태계를 포함한 완전한 관측 플랫폼으로서 상업용(Grafana Cloud, Enterprise) 버전과 오픈소스 버전이 동일 모노레포에서 빌드 태그(oss, enterprise, pro)로 분기된다.

2. 저장소 구조 분석

grafana_grafana/
├── pkg/              ← Go 백엔드 (api, services, server, plugins, infra, tsdb 등)
├── public/app/       ← React 프론트엔드 (features/<domain>별 슬라이스)
├── packages/         ← 공유 TS 라이브러리 (@grafana/ui, data, runtime, schema 등)
├── apps/             ← App SDK 기반 스탠드얼론 Go 앱 (dashboard, alerting, folder 등)
├── kinds/            ← CUE 스키마 정의 (코드 자동 생성 원본)
├── e2e-playwright/   ← Playwright E2E 테스트
├── devenv/           ← 로컬 개발 Docker Compose 환경
├── docs/             ← 공식 문서
├── scripts/          ← CI/빌드 유틸리티 스크립트
├── .github/          ← 89개 CI 워크플로우, Dependabot, Renovate
├── conf/             ← defaults.ini / custom.ini 설정
└── Dockerfile        ← 멀티스테이지 빌드
  • 모노레포 구성, Yarn Workspaces(프론트엔드) + Go Workspaces(백엔드)
  • 코드(기능)와 운영 자산(devenv, packaging, conf)이 명확히 분리
  • 도메인 지향 구조: 백엔드 pkg/services/<domain>, 프론트엔드 public/app/features/<domain>

4. 아키텍처 분석

백엔드: - 진입점: pkg/cmd/grafana/main.go → cli.App → grafana-server 서브커맨드 - 부트스트랩: pkg/server/wire.go (Wire 컴파일타임 DI 그래프) - 레이어: pkg/api/ (HTTP 핸들러·라우팅) → pkg/services/<domain>/ (비즈니스 로직) → pkg/infra/db/ (DB 추상화 인터페이스) → pkg/services/sqlstore/ (xorm 구현) - 플러그인: gRPC/ConnectRPC로 격리된 프로세스 통신, 플러그인 SDK(grafana-plugin-sdk-go) 기반 - 피처 플래그: pkg/services/featuremgmt/ 코드 자동 생성 (make gen-feature-toggles) - 스탠드얼론 앱: apps/ 디렉터리에 Kubernetes Operator 패턴(App SDK) 적용

프론트엔드: - 피처 슬라이스 구조: public/app/features/<domain>/ (alerting, dashboard, explore, datasources 등) - 상태: Redux Toolkit 슬라이스 + RTK Query (서버 상태) - 공유 컴포넌트: @grafana/ui, @grafana/data, @grafana/runtime, @grafana/scenes - 국제화: i18next + Crowdin 연동

통신: - 프론트엔드 ↔ 백엔드: REST HTTP API - 백엔드 ↔ 플러그인: gRPC (Plugin SDK) - 백엔드 ↔ 외부 데이터소스: 각 플러그인 구현체가 직접 처리 (HTTP, gRPC 등)

강점 (Strengths)

  1. 성숙한 엔터프라이즈급 모노레포 설계: Go Workspaces + Yarn Workspaces를 결합한 하이브리드 모노레포로, 백엔드/프론트엔드/공유 라이브러리/스탠드얼론 앱을 단일 레포에서 일관성 있게 관리하면서 각 영역의 독립 빌드·배포 사이클을 유지한다.

  2. Wire DI 기반 컴파일타임 안전성: Google Wire를 통해 의존성 그래프를 컴파일 타임에 검증, 순환 의존성·누락 바인딩을 런타임 전에 포착한다. 대형 Go 서비스에서 보기 드문 강력한 안전망이다.

  3. CUE 스키마 기반 코드 생성: kinds/ 디렉터리의 CUE 정의에서 Go·TypeScript 코드를 동시 생성(make gen-cue), 프론트-백엔드 타입 동기화를 자동화한다. 대시보드 스키마 진화의 안정성을 보장하는 핵심 메커니즘이다.

  4. 89개 워크플로우로 구성된 정밀한 CI/CD 파이프라인: 변경 감지 기반 선택적 실행, 8-샤드 병렬 백엔드 테스트, 브랜치 전략별 분기 실행, 보안 패치 자동화까지 갖춘 산업 수준의 CI 인프라다.

  5. 이중 라이선스 전략(AGPL-3.0 + Apache-2.0): 핵심 플랫폼은 AGPL로 상업적 fork를 억제하면서, 플러그인/SDK 패키지는 Apache-2.0으로 오픈 생태계를 육성하는 전략적 라이선스 구조다.

위험/개선 필요 사항 (Risks & Areas for Improvement)

  1. React 18 잠금(React 19 마이그레이션 미완료): renovate.json5에서 React, @types/react, react-router-dom 등 핵심 의존성이 명시적으로 업데이트 무시 처리되어 있다. 에픽(#98813)으로 추적 중이나, 지연될수록 마이그레이션 난이도와 보안 리스크가 증가한다.

  2. SECURITY.md 부재: 루트 레벨에 SECURITY.md가 없어 gh나 표준 도구가 보안 정책을 자동 탐지하지 못한다. GitHub 레포 설정에 의존하는 구조는 포크된 환경이나 미러 레포에서 정책이 유실될 수 있다.

  3. 대규모 의존성 그래프로 인한 빌드 지연: pkg/api/ 등 대형 패키지는 테스트 컴파일에 최대 2분이 소요된다고 AGENTS.md에 명시되어 있다. 개발 피드백 루프 지연은 장기적으로 생산성 저하 요인이 된다.

  4. 단일 저장소 크기 및 CODEOWNERS 복잡도: 89개 워크플로우, 수십 개의 CODEOWNER 팀, 다수의 Yarn 워크스페이스가 결합된 환경은 신규 기여자의 진입 장벽을 높이며, CI 유지보수 비용도 상당하다.

  5. 통합 테스트의 외부 DB 의존성: PostgreSQL/MySQL 통합 테스트는 devenv Docker 환경이 필요하며, relyance.yaml의 서비스 매핑이 비어 있어 SBOM 및 공급망 가시성이 아직 성숙하지 않다.

도입 권고 (Adoption Recommendation)

기술 도입 관점: Grafana는 관측 가능성 플랫폼 분야에서 사실상의 표준(de facto standard)이다. 자체 모니터링 플랫폼 구축을 고려 중이라면 처음부터 개발하기보다 Grafana를 기반으로 확장하는 것을 강력히 권고한다. 플러그인 아키텍처가 잘 설계되어 있어 커스텀 데이터소스·패널·앱 개발이 용이하다.

아키텍처 벤치마킹 관점: Wire DI 패턴, CUE 기반 스키마 코드 생성, 피처 슬라이스 구조, 변경 감지 기반 CI 최적화는 대규모 Go + React 모노레포를 구축하는 팀이 참고할 수 있는 검증된 패턴이다.

보안 검토 관점: AGPL 라이선스 의무(네트워크 사용 포함 소스 공개)를 확인해야 한다. 내부 사용은 문제없으나, SaaS로 제공하거나 수정 버전을 배포할 경우 법률 검토가 필수다.

기여 준비도 관점: 문서화·템플릿·자동화가 완비되어 있으나, 빌드 환경(GCC, 특정 Go/Node 버전) 요구사항과 대규모 코드베이스 파악에 초기 투자가 필요하다. beginner-friendly 레이블 이슈로 시작하는 것을 권장한다.

운영 성숙도 평가: 최상위 등급 (Production-Ready, Enterprise-Grade). 13년 이상의 역사, 수천 명의 기여자, 글로벌 커뮤니티, 엔터프라이즈 지원 체계를 갖춘 프로젝트다. 미션 크리티컬 인프라에 바로 도입 가능하다.
