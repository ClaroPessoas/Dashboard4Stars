프로젝트 개요 (Project Overview)

TREK는 셀프 호스팅 방식의 실시간 협업 여행 플래너 애플리케이션입니다. 지도, 예산 추적, 패킹 리스트, 여행 일지, AI/MCP 통합을 포함하며, 개인 또는 팀 단위 사용을 위한 PWA(Progressive Web App)로 설계되었습니다. Docker를 통한 단일 컨테이너 배포를 지원하며 Helm/Kubernetes 차트도 제공됩니다.

1. 강점 (Strengths)

  1. 통합된 API 계약 레이어: shared 패키지의 Zod 스키마가 서버와 클라이언트 간 타입 단일 소스 역할을 하여, CI에서 i18n 패리티와 타입 일관성을 자동 검증합니다. 런타임 에러보다 빌드 타임에 계약 불일치를 잡아냅니다.

  2. 심층적 보안 설계: 단순한 인증 미들웨어를 넘어서 SSRF 방어(ssrfGuard.ts)에서 DNS 핀닝, IPv4-매핑 IPv6 처리, CGNAT/Tailscale 대역 차단까지 구현되어 있습니다. WebAuthn Passkey, TOTP MFA, OAuth 2.1, OIDC를 모두 지원하는 다층 인증 체계는 셀프 호스팅 앱 기준으로 매우 드문 수준입니다.

  3. 오프라인 First PWA 아키텍처: Dexie/IndexedDB 기반의 오프라인 캐시, 뮤테이션 큐(mutationQueue.ts), 의존성 체인 처리(임시 음수 ID → 실 ID 교체), Workbox 타일 프리페치가 유기적으로 결합된 완성도 높은 오프라인 경험을 제공합니다.

  4. MCP(Model Context Protocol) 선도적 통합: 150+ AI 도구와 30개 리소스를 OAuth 2.1 인증으로 노출하는 내장 MCP 서버는 AI 에이전트 워크플로우와의 통합에서 경쟁 제품 대비 명확한 차별점입니다.

  5. 프로덕션 급 컨테이너 하드닝: read_only 파일시스템, cap_drop: ALL, no-new-privileges, tmpfs, dumb-init, gosu를 통한 비루트 실행, 멀티 스테이지 빌드(소스 코드 최종 이미지 미포함), Docker Scout CVE 게이트가 결합된 Docker 이미지는 보안 모범 사례를 충실히 따릅니다.

2. 위험 / 개선 필요 사항 (Risks & Areas for Improvement)

  1. SQLite 단일 서버 제약: SQLite는 동시 쓰기 부하가 증가하면 병목이 됩니다. 현재 설계로는 수평 확장(복수 컨테이너)이 불가능하며, 사용자 증가 시 PostgreSQL 마이그레이션 경로가 없습니다. 마이그레이션 코드(3,079줄 단일 파일)도 리뷰와 관리가 점점 어려워집니다.

  2. Dependabot 설정 파일 부재: SECURITY.md에서 Dependabot 언급은 있지만 .github/dependabot.yml 파일이 저장소에 없습니다. 의존성 자동 업데이트가 비활성화되어 있거나 조직 수준 설정에만 의존할 가능성이 있습니다. 취약한 npm 패키지 노출 시간이 길어질 수 있습니다.

  3. 레거시 코드 커버리지 게이트 없음: 서버의 80% 커버리지 임계값은 src/nest/**/*.ts (NestJS 신규 코드)에만 적용됩니다. 레거시 서비스/유틸리티 코드(src/services/, src/middleware/ 등)는 커버리지 게이트가 없어 회귀 위험이 있습니다.

  4. CHANGELOG 파일 부재: CHANGELOG.md가 없고 GitHub Releases에만 릴리즈 정보가 있습니다. 설치 후 업데이트 시 변경 사항을 확인하려면 GitHub 접근이 필수이며, 에어갭(air-gapped) 환경 운영자에게는 불편합니다.

  5. OIDC 클라이언트 시크릿 환경 변수 노출: OIDC_CLIENT_SECRET을 포함한 민감 값들이 환경 변수로 관리됩니다. Kubernetes 환경에서는 Helm 차트의 existingSecret 옵션을 안내하지만, Docker Compose 예제에서는 .env 파일 보안에 대한 명시적 경고가 없습니다.

Step 4: 아키텍처

서버 아키텍처: - NestJS 모듈 기반 도메인 분리: AppModule에 30+ 도메인 모듈 등록 - bootstrap.ts가 미들웨어 적용 순서를 명시적으로 제어 (Helmet → CORS → HSTS → MFA 정책 → 요청 로깅 → 업로드 라우트 → MCP/OAuth/플랫폼 라우트 → 정적 파일 → NestJS 라우터) - SpaFallbackFilter + TrekExceptionFilter: 전역 에러 봉투와 SPA 폴백 분리 - IdempotencyInterceptor: 클라이언트 재시도 시 이중 적용 방지 - WebSocket 서버(ws 라이브러리)가 동일 HTTP 서버에 마운트, /ws 경로 - MCP 서버: StreamableHTTP 트랜스포트 + OAuth 2.1 인증 게이트

클라이언트 아키텍처: - Zustand store + 도메인별 슬라이스 (placesSlice, daysSlice 등) - remoteEventHandler.ts: WebSocket 이벤트 → Zustand 상태 업데이트 → Dexie write-through - mutationQueue.ts: 오프라인 뮤테이션 큐 (임시 음수 ID, 의존성 체인 해소) - tripSyncManager.ts: 재연결 시 서버 상태 diff/sync - React Router v6 기반 SPA 라우팅

레이어 분리 수준: 프레젠테이션(React 컴포넌트) → 스토어(Zustand 슬라이스) → API 클라이언트(axios) → WebSocket 싱크. 서버 측은 Controller → Service → DB(raw SQL via better-sqlite3) 패턴. 현재 ORM 없이 직접 SQL을 사용하여 쿼리 유연성은 높으나 타입 안전성은 수동 관리.

Step 6: 보안 및 공급망

보안 정책: SECURITY.md 존재, 비공개 보고 이메일(report@liketrek.com), 48시간 응답 약속.

SSRF 방어 (server/src/utils/ssrfGuard.ts): - DNS 핀닝: 해석된 IP를 캐시하고 리디렉션 시 동일 IP 강제 - 항상 차단: 루프백(127.x/::1), 미지정(0.x), 링크-로컬(169.254.x/fe80::), IPv4-매핑 루프백/링크-로컬 - 환경 변수 제어 차단: RFC-1918(10.x/172.16-31.x/192.168.x), CGNAT/Tailscale(100.64/10), IPv6 ULA
