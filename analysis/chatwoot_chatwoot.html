1. 목적 및 범위 / Purpose & Scope

Chatwoot은 기업용 오픈소스 고객 지원 플랫폼으로, SaaS 형태로 제공되거나 자체 호스팅이 가능하다.

  • 해결 문제: 기업이 다수의 채널(라이브챗, 이메일, Facebook, Instagram, Twitter/X, WhatsApp, Telegram, Line, SMS, TikTok)을 단일 에이전트 워크스페이스에서 관리하기 어려운 문제
  • 대상 사용자: 고객지원팀, 소규모~대형 SaaS 기업, 자체호스팅을 원하는 조직
  • 성격: 풀스택 애플리케이션 플랫폼 (라이브러리나 프레임워크가 아닌, 배포 가능한 독립 제품)
  • 최신 기능: Captain AI Agent(LLM 기반 지원), pgvector를 활용한 AI 벡터 검색, CRM 통합

2. 저장소 구조 분석 / Repository Structure

chatwoot_chatwoot/
├── app/                    # Rails 메인 애플리케이션 (MVC + 확장 계층)
│   ├── actions/            # Command/Action 패턴 클래스
│   ├── builders/           # 복잡 객체 생성 Builder 패턴
│   ├── channels/           # ActionCable WebSocket 채널
│   ├── controllers/        # Rails 컨트롤러
│   ├── dispatchers/        # 이벤트 발행자 (Event Dispatcher)
│   ├── finders/            # 복잡 쿼리 Finder 클래스

│   ├── jobs/               # Sidekiq 백그라운드 잡

│   ├── models/             # ActiveRecord 모델 (105개+)
│   ├── policies/           # Pundit 인가 정책
│   └── services/           # 서비스 레이어 (198개 파일)
├── config/                 # Rails 설정, 라우팅, DB
├── db/                     # 스키마 및 마이그레이션
├── enterprise/             # EE 오버레이 (OSS 코어 확장)
├── spec/                   # RSpec 테스트 (29개 서브디렉토리)
├── swagger/                # OpenAPI/Swagger API 문서
├── docker/                 # Dockerfile, 컴포즈, entrypoints
├── deployment/             # nginx, systemd 설정
├── .github/workflows/      # 16개 GitHub Actions 워크플로
└── lib/                    # 유틸리티, 커스텀 예외, 태스크

구조 평가: - 코드(app/)와 운영 자산(deployment/, docker/)이 명확히 분리 - 단일 저장소(모노레포): 백엔드·프론트엔드·엔터프라이즈가 하나의 repo에 공존 - 도메인 지향 + 레이어 지향 혼합: 모델은 도메인 경계, 서비스·컨트롤러는 레이어 경계

4. 아키텍처 분석 / Architecture

진입점

  • HTTP API: config/routes.rb → Api::V1::* 네임스페이스 컨트롤러
  • 프론트엔드: app/javascript/entrypoints/ → Vite 번들 → Vue Router SPA
  • 실시간: ActionCable 채널 (app/channels/)
  • 이메일 인입: ActionMailbox (app/mailboxes/)
  • 백그라운드: Sidekiq → app/jobs/

아키텍처 패턴

요청 흐름:
HTTP Request
  → ApplicationController (DeviseTokenAuth + Pundit + SwitchLocale)
    → Controller#action
      → Finder (쿼리 추상화)
      → Service (비즈니스 로직)
        → Builder (복잡 객체 생성)
        → Dispatcher (이벤트 발행)
          → Listener (이벤트 구독, 비동기 처리)
            → Job (Sidekiq 백그라운드)

주요 패턴:

  1. Service Layer 패턴: app/services/에 198개 서비스 파일. 채널별(facebook, instagram, whatsapp…), 도메인별(conversations, contacts, messages…) 분리
  2. Event-Driven 패턴: Dispatchers → Listeners 구조로 채널 간 이벤트 비동기 처리
  3. Policy Object 패턴: Pundit을 통한 RBAC (역할 기반 접근 제어)
  4. Finder 패턴: 복잡 DB 쿼리를 컨트롤러에서 분리
  5. Enterprise 오버레이: prepend_mod_with / include_mod_with 패턴으로 EE 기능을 OSS 코어에 비침습적으로 주입

채널 추상화

12개 채널(Web Widget, Email, Facebook, Instagram, Twitter, WhatsApp, Telegram, Line, SMS, TikTok 등)이 Channel::* 모델로 추상화되어 Inbox 를 통해 동일한 Conversation / Message 인터페이스 사용.

프론트엔드 아키텍처

app/javascript/
├── dashboard/      → 메인 에이전트 인터페이스 (가장 큰 앱)
├── widget/         → 임베드 채팅 위젯 (독립 빌드)
├── portal/         → 고객 Help Center 포털
├── v3/             → 신규 Vue 3 컴포넌트 (마이그레이션 중)
├── design-system/  → 재사용 컴포넌트 라이브러리
├── sdk/            → JavaScript 임베드 SDK
└── shared/         → 공통 컴포저블, 유틸리티

상태 관리는 Pinia Store, API 통신은 Axios, 실시간은 ActionCable 클라이언트.

8. 강점 / Strengths

  1. 명확한 도메인 + 레이어 분리: Services/Finders/Builders/Dispatchers/Listeners/Policies의 역할 분담이 198개 서비스 파일에도 불구하고 유지되어 대규모 팀 협업에 적합
  2. Enterprise 오버레이 아키텍처: prepend_mod_with 패턴으로 OSS 코어를 수정하지 않고 EE 기능 주입 가능. 오픈소스 생태계와 상업화 전략의 모범 사례
  3. 옴니채널 추상화 설계: 12개 채널이 Channel::* → Inbox → Conversation → Message 단일 인터페이스로 통합되어 신규 채널 추가가 용이
  4. 강력한 CI/CD 파이프라인: 16노드 병렬 RSpec, 분리된 Lint/FE/BE 워크플로, 야간 설치 검증, Docker 이미지 자동화 — 대형 오픈소스 프로젝트 수준의 자동화
  5. AI/LLM 준비 스택: pgvector 통합으로 벡터 검색, LLM Formatter 서비스, Captain AI Agent — 최신 AI 트렌드를 코어에 선제적으로 통합

9. 위험 / 개선 필요 사항 / Risks & Improvements

  1. 모놀리식 규모 증가: 105개 모델, 198개 서비스 파일이 단일 Rails 앱에 집중. 특정 도메인(채널, AI, 결제)의 독립적 스케일아웃이 어려우며, 향후 마이크로서비스 분리 필요성 가능성
  2. 프론트엔드 마이그레이션 부채: v3/, components-next/의 존재는 Vue 2→3 또는 구 아키텍처→신 아키텍처 마이그레이션이 진행 중임을 의미. 이 과도기 상태는 새 기여자에게 혼란 야기 가능
  3. SBOM 및 아티팩트 서명 부재: FOSS 배포에서 SBOM(Software Bill of Materials) 파일과 컨테이너 이미지 서명(Sigstore/Cosign)이 명시적으로 없음. 공급망 보안 강화 요구가 높아지는 추세에서 개선 필요
  4. Elasticsearch 선택적 의존성 복잡성: 전문 검색 기능이 Elasticsearch 설치 여부에 따라 동작이 달라지는 조건부 의존성이 테스트 및 배포 복잡도를 높임
  5. 최신 버전만 지원 정책: 패치 지원이 최신 버전만으로 제한되어 자체호스팅 기업이 지속적인 버전 업그레이드를 강요받음. 기업 환경에서 업그레이드 주기가 긴 경우 보안 공백 발생 가능
