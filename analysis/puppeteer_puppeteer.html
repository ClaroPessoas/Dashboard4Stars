1. 목적 및 범위 (Purpose & Scope)

Puppeteer는 Chrome/Firefox 브라우저를 DevTools Protocol(CDP) 또는 WebDriver BiDi 프로토콜로 프로그래밍 방식으로 제어하는 Node.js 고수준 API 라이브러리다. Google Chrome 팀이 관리하는 공식 오픈소스 프로젝트로, 주요 사용 사례는 다음과 같다:

  • 웹 스크래핑 / 자동화: 헤드리스 브라우저 기반 콘텐츠 추출
  • E2E 테스트: 브라우저 수준 UI 자동화 테스트
  • PDF/Screenshot 생성: 서버사이드 렌더링 캡처
  • 성능 분석: DevTools API를 통한 타이밍·리소스 측정
  • MCP(Model Context Protocol) 통합: LLM 에이전트의 브라우저 제어

대상 사용자: 웹 자동화가 필요한 개발자, QA 엔지니어, DevOps/인프라 팀, AI 에이전트 개발자

3-1. 리포지토리 구조

puppeteer/
├── packages/
│   ├── puppeteer/           # 사용자용: 브라우저 자동 다운로드 포함
│   ├── puppeteer-core/      # 라이브러리 전용: 브라우저 없음
│   │   └── src/
│   │       ├── api/         # 공개 API 클래스 (Browser, Page, Frame 등)
│   │       ├── bidi/        # WebDriver BiDi 프로토콜 구현
│   │       ├── cdp/         # Chrome DevTools Protocol 구현
│   │       ├── common/      # 공유 유틸, 이벤트, 쿼리 핸들러
│   │       ├── injected/    # 페이지에 주입되는 스크립트
│   │       └── node/        # Node.js 전용 브라우저 실행 로직
│   ├── browsers/            # @puppeteer/browsers 다운로드·실행 관리
│   ├── ng-schematics/       # Angular CLI 통합 스키매틱
│   └── testserver/          # 테스트용 HTTP/HTTPS 서버
├── tools/
│   ├── docgen/              # TSDoc → Markdown API 문서 생성기
│   ├── doctest/             # 문서 코드 예제 실행 테스터
│   ├── mocha-runner/        # CDP/BiDi 전환 가능한 Mocha 커스텀 러너
│   └── eslint/              # Puppeteer 전용 ESLint 플러그인
├── test/                    # E2E·통합 테스트 (TestExpectations.json 포함)
├── website/                 # Docusaurus 문서 사이트
├── docker/                  # Dockerfile, 패키지 번들 스크립트
└── examples/                # 사용 예제

구조 특징: 코드(packages/)와 운영 자산(tools/, .github/)이 명확히 분리되어 있으며, 기능 지향과 레이어 지향이 혼합된 하이브리드 구조다.

4. 강점 (Strengths)

  1. 듀얼 프로토콜 추상화 아키텍처: api/ 레이어가 CDP와 WebDriver BiDi를 모두 지원하도록 설계되어, Chrome과 Firefox를 단일 API로 제어 가능. 향후 새 프로토콜 추가 시 기존 API 변경 불필요한 확장성 보유

  2. 엔터프라이즈급 CI/CD 인프라: 7개 브라우저×모드 조합의 매트릭스 테스트, 일일 테스트, 플래키 감지 워크플로우, OIDC 기반 NPM 프로버넌스 퍼블리시까지 공급망 보안을 고려한 완전 자동화 파이프라인

  3. Wireit 기반 증분 빌드 캐싱: 모노레포 환경에서 변경된 패키지만 재빌드하는 Wireit 태스크 오케스트레이션으로 개발 생산성 및 CI 효율 극대화

  4. TypeScript 엄격 모드 + API Extractor: noUncheckedIndexedAccess, strictNullChecks 등 최고 수준의 타입 안전성과 @microsoft/api-extractor를 통한 공개 API 표면 명시적 관리로 하위 호환성 보장

  5. 문서-코드 일관성 보장: tools/doctest/가 README·문서의 코드 예제를 실제 실행하여 검증함으로써 문서가 항상 동작하는 코드임을 CI에서 보증

5. 위험 / 개선 필요 사항 (Risks & Improvements)

  1. 의존성 자동 갱신 미설정: Dependabot 또는 Renovate가 없어 devtools-protocol, chromium-bidi 등 주요 의존성의 취약점 패치가 수동 관리에 의존. 특히 ws (WebSocket 라이브러리)와 같은 전이 의존성의 취약점 노출 위험 존재

  2. Node.js ≥22 요구 조건: package.json의 engines.node >= 22.12.0 조건이 엔터프라이즈 환경의 도입 장벽이 될 수 있음. LTS 사이클에 맞춘 지원 정책 명문화 필요

  3. Page.ts의 과도한 크기 (103KB): api/Page.ts가 103KB에 달해 단일 파일에 과도한 책임이 집중됨. 유지보수 복잡도와 PR 충돌 위험이 높으며, 도메인별 분리 리팩토링이 장기적으로 필요

  4. ADR(Architecture Decision Record) 부재: BiDi 전환, ESM 전환, Node 22 요구 조건 등 주요 아키텍처 결정의 근거가 코드나 CHANGELOG에만 분산되어 있고 체계적으로 문서화되지 않아 신규 기여자의 맥락 파악이 어려움

  5. TestExpectations.json 증가 부채: 89KB에 달하는 테스트 기대값 파일이 플랫폼별 스킵 항목 누적으로 계속 증가하는 구조. 주기적 정리 정책 없이는 테스트 신뢰성 지표가 희석될 위험

6. 도입 권고 (Adoption Recommendation)

기술 도입 관점

강력 권고: 브라우저 자동화 프로젝트의 사실상 표준 라이브러리. Google Chrome 팀의 직접 유지관리로 DevTools Protocol 최신 기능의 즉각적 지원이 보장된다. WebDriver BiDi 지원으로 Selenium/WebDriver 기반 프로젝트의 마이그레이션 경로도 제공한다.

아키텍처 벤치마킹 관점

참고 권장: 모노레포 구성(Wireit + npm workspaces), 듀얼 프로토콜 추상화 패턴, CI 매트릭스 설계, 문서 코드 테스트(doctest) 방식은 유사 규모의 오픈소스 라이브러리 설계 시 참고할 수 있는 우수 사례다.

보안 검토 관점

조건부 적합: OIDC 프로버넌스와 Scorecards 분석은 공급망 보안 요구사항을 충족하나, Dependabot/Renovate 미설정으로 인한 의존성 취약점 모니터링 공백을 도입 조직에서 자체 보완해야 한다.

기여 준비도 관점

준비 완료: CONTRIBUTING.md, 코드 스타일 자동화(ESLint + Prettier), conventional commit 검증, 이슈/PR 템플릿, Stale 관리까지 갖춰진 성숙한 기여 환경이다. 다만 복잡한 테스트 매트릭스와 로컬 브라우저 환경 설정이 초기 기여의 진입 장벽으로 작용할 수 있다.
