1. 프로젝트 개요 / Project Overview

1.1 목적 및 분류 / Purpose and Classification

해결하는 문제 / Problem solved LiteParse는 PDF 및 다양한 문서 형식(DOCX, XLSX, PPTX, 이미지)으로부터 고품질의 공간 인식 텍스트(bounding box 포함)를 로컬에서 추출하는 도구입니다. 클라우드 의존 없이 빠르고 가벼운 문서 파싱을 제공하며, OCR(Tesseract 내장 또는 외부 HTTP 서버), 레이아웃 재구성(Grid Projection), 스크린샷 생성을 지원합니다.

LiteParse solves the problem of fast, lightweight local PDF/document parsing with spatial text extraction, bounding boxes, and optional OCR — without cloud dependencies or LLM integrations.

분류 / Classification: Library + CLI Tool (multi-language bindings)

9. 자주 묻는 질문 / FAQ

[한국어]

Q1. cargo build를 실행했는데 _Py* 또는 _Napi* 링크 에러가 납니다.

A. 워크스페이스 전체 빌드는 의도적으로 지원하지 않습니다. Python/Node.js 바인딩 크레이트는 각각 maturin과 napi CLI를 통해서만 올바르게 링크됩니다. 코어만 빌드하려면:

cargo build -p liteparse

Q2. OCR이 실행되지 않거나 "tessdata" 관련 에러가 납니다.

A. 첫 실행 시 tesseract-rs가 tessdata를 자동 다운로드합니다. 인터넷 연결이 없거나 에어갭 환경이라면 tessdata 파일을 미리 준비하고 경로를 지정하세요:

export TESSDATA_PREFIX=/path/to/tessdata
lit parse document.pdf --ocr-language eng
# 또는
lit parse document.pdf --tessdata-path /path/to/tessdata

Q3. DOCX/XLSX 파일을 파싱하려고 하면 변환 오류가 납니다.

A. 비PDF 포맷 변환에는 LibreOffice가 필요합니다. 설치 후 PATH에 추가하세요:

# Ubuntu/Debian
sudo apt-get install libreoffice
# macOS
brew install --cask libreoffice
# Windows: LibreOffice 설치 후 C:\Program Files\LibreOffice\program을 PATH에 추가

Q4. 이미지 파싱에 실패합니다.

A. 이미지 변환에는 ImageMagick이 필요합니다:

# Ubuntu/Debian
sudo apt-get install imagemagick
# macOS
brew install imagemagick

Q5. cargo build 중 pdfium 다운로드가 실패하거나 느립니다.

A. pdfium-sys build.rs가 GitHub에서 PDFium 공유 라이브러리를 자동 다운로드합니다. 네트워크 상태를 확인하고 재시도하세요. 캐시 위치: ~/.cache/pdfium-rs (Linux/macOS), %LOCALAPPDATA%\pdfium-rs (Windows).

Q6. 그리드 프로젝션 출력이 예상과 다릅니다. 어떻게 디버깅하나요?

A. --debug 및 --debug-visualize 플래그를 사용하세요:

lit parse document.pdf --debug --debug-page 1
lit parse document.pdf --debug-visualize --debug-output ./debug-out
# debug-out/에 색상 코딩된 PNG가 생성됨 (파란색=왼쪽정렬, 빨간색=오른쪽, 녹색=가운데, 회색=떠있음)

[English]

Q1. cargo build gives _Py* or _Napi* linker errors.

A. Workspace-wide build is intentionally unsupported. Python/Node.js binding crates require their respective CLI tools (maturin / napi) to resolve linker symbols. To build the core only:

cargo build -p liteparse

Q2. OCR doesn't run or I get tessdata-related errors.

A. On first run, tesseract-rs auto-downloads tessdata. In offline or air-gapped environments, provide tessdata manually:

export TESSDATA_PREFIX=/path/to/tessdata
lit parse document.pdf --ocr-language eng
# Or pass the path directly:
lit parse document.pdf --tessdata-path /path/to/tessdata

Q3. Parsing DOCX/XLSX files fails with a conversion error.

A. Non-PDF format conversion requires LibreOffice. Install it and ensure it's on your PATH:

# Ubuntu/Debian
sudo apt-get install libreoffice
# macOS
brew install --cask libreoffice
# Windows: install LibreOffice and add C:\Program Files\LibreOffice\program to PATH

Q4. Image parsing fails.

A. Image-to-PDF conversion requires ImageMagick:

# Ubuntu/Debian
sudo apt-get install imagemagick
# macOS
brew install imagemagick

Q5. PDFium download hangs or fails during cargo build.

A. The pdfium-sys build script auto-downloads the PDFium shared library from GitHub. Check your network and retry. The cache lives at ~/.cache/pdfium-rs (Linux/macOS) or %LOCALAPPDATA%\pdfium-rs (Windows).

Q6. Grid projection output looks wrong. How do I debug it?

A. Use the --debug and --debug-visualize flags:

lit parse document.pdf --debug --debug-page 1
lit parse document.pdf --debug-visualize --debug-output ./debug-out
# Produces color-coded PNGs: blue=left-snap, red=right, green=center, gray=floating

[한국어]

[English]

Classification: Standalone parsing library + CLI tool

LiteParse is a multi-language Rust library for extracting structured text from PDF and document files locally. It primarily solves:

  • RAG/LLM pipeline preprocessing: structured text + bounding box extraction to feed documents into LLMs
  • Automated document processing: batch-process PDFs, Office documents, and images via CLI or API
  • Scanned-document OCR: text extraction from image-based PDFs (Tesseract bundled)
  • Visual document understanding: page screenshot generation for LLM agents
  • Multi-platform embedding: same API surface in Rust, Node.js, Python, or the browser (WASM)

It is especially valuable when you need to process sensitive documents without sending them to a cloud service, or when you want to avoid per-page API costs.

시나리오 2: Node.js 서버에서 문서 파싱 API 구축

Express 서버에서 업로드된 PDF를 파싱하여 구조화된 JSON을 반환.

// npm install @llamaindex/liteparse express multer
import { LiteParse } from '@llamaindex/liteparse';
import express from 'express';
import multer from 'multer';

const upload = multer({ storage: multer.memoryStorage() });
const app = express();

const parser = new LiteParse({
  ocrEnabled: true,
  outputFormat: 'json',
  maxPages: 50,
});

app.post('/parse', upload.single('file'), async (req, res) => {
  if (!req.file) return res.status(400).json({ error: 'No file uploaded' });

  try {
    // 파일 버퍼를 직접 전달 (파일 저장 불필요)
    const result = await parser.parse(req.file.buffer);
    res.json({
      pageCount: result.pages.length,
      text: result.text,
      pages: result.pages.map(p => ({
        pageNum: p.pageNum,
        itemCount: p.textItems.length,
      })),
    });
  } catch (err) {
    res.status(500).json({ error: String(err) });
  }
});

6. 성능 및 확장성 고려사항 / Performance & Scalability

[한국어]

알려진 성능 특성

  • PDFium 텍스트 추출은 매우 빠름 — 수백 페이지 문서도 수초 내 처리
  • OCR이 주요 병목: 페이지당 Tesseract 실행 시간이 텍스트 추출보다 수십 배 느림
  • --num-workers N 옵션으로 OCR을 병렬화 가능 (기본: CPU 코어 - 1)
  • --no-ocr 플래그로 OCR을 비활성화하면 처리 속도 대폭 향상
  • HTTP OCR 서버(EasyOCR, PaddleOCR)는 GPU 활용 시 Tesseract보다 빠를 수 있음

수평 확장 전략

LiteParse는 상태가 없는(stateless) 단일 바이너리이므로 수평 확장이 용이합니다:

# 문서를 청크로 나누어 병렬 처리
lit parse doc.pdf --target-pages "1-50" -o chunk1.json &
lit parse doc.pdf --target-pages "51-100" -o chunk2.json &
wait

# Kubernetes: 여러 Pod에서 독립적으로 실행
# 각 Pod가 별도 문서 또는 페이지 범위 처리

메모리 고려사항

  • 대용량 PDF(1000+ 페이지)는 상당한 메모리 사용 가능
  • --max-pages N으로 페이지 수 제한
  • Docker 컨테이너에서 메모리 제한 설정 권장 (--memory 2g)

캐싱 전략

LiteParse 자체에는 캐싱이 없습니다. 애플리케이션 레이어에서: - 파일 해시를 키로 파싱 결과 캐싱 (같은 파일 반복 파싱 방지) - LLM 파이프라인에서는 파싱 결과를 벡터 DB에 저장하여 재파싱 회피

모니터링 및 로깅

  • --quiet 플래그로 진행 상황 출력 억제 (프로덕션 배포 권장)
  • stderr에 오류 출력, stdout에 파싱 결과 출력 (파이프라인 친화적)
  • 에러는 LiteParseError 타입으로 구조화되어 있어 프로그래밍 방식 처리 가능

참고: 공식 문서 기반 권장 사항 / Note: Recommended based on official documentation and project source analysis

[English]

Known performance characteristics

  • PDFium text extraction is very fast — hundreds of pages parsed in seconds
  • OCR is the primary bottleneck: Tesseract is orders of magnitude slower than native extraction
  • --num-workers N parallelizes OCR (default: CPU cores - 1)
  • --no-ocr disables OCR entirely and yields the fastest parse times
  • HTTP OCR servers (EasyOCR, PaddleOCR) with GPU can outperform Tesseract significantly

Horizontal scaling

LiteParse is a stateless single binary, making horizontal scaling straightforward:

# Split large documents across parallel processes
lit parse doc.pdf --target-pages "1-50" -o chunk1.json &
lit parse doc.pdf --target-pages "51-100" -o chunk2.json &
wait

# Kubernetes: run independent pods, each processing a different document or page range

Memory considerations

  • Very large PDFs (1000+ pages) can consume significant memory
  • Use --max-pages N to cap pages
  • Set memory limits when running in Docker (--memory 2g)

Caching strategy

LiteParse itself has no caching layer. At the application level: - Cache parse results by file hash to avoid re-parsing the same document - In LLM pipelines, persist parsed results to a vector store to skip re-parsing

Monitoring and logging

  • Use --quiet to suppress progress output in production deployments
  • Errors go to stderr; parse results to stdout — pipeline-friendly
  • Errors are typed as LiteParseError for programmatic handling
