상세 분석

Step 1. 목적 및 범위

DESIGN.md는 AI 코딩 에이전트(특히 Claude Code 등)가 일관된 UI를 생성할 수 있도록 디자인 시스템을 기술하는 포맷 명세 + CLI 검증 도구다. 핵심 통찰은 "토큰 수치보다 산문(prose)이 디자인 의도를 더 잘 전달한다"는 점이며, PHILOSOPHY.md에 이를 상세히 설명한다.

대상 사용자: - AI 코딩 에이전트와 협업하는 프론트엔드 개발자 - 디자인 시스템 관리자 - AI 에이전트 통합을 구축하는 플랫폼 엔지니어

분류: CLI 도구 + npm 라이브러리 (에이전트 우선 설계 철학)

Step 2. 저장소 구조 분석

google-labs-code/design.md/
├── .agents/skills/          # Claude Code 에이전트 스킬 (ink, opentui, tdd, typed-service-contracts, agent-dx-cli-scale)
├── .github/workflows/       # CI 워크플로 (test.yml 단일)
├── docs/                    # spec.md (자동 생성)
├── examples/                # 예시 DESIGN.md 파일 (atmospheric-glass, paws-and-paths, totality-festival)
├── packages/cli/            # 단일 퍼블리시 패키지 (@google/design.md)
│   └── src/
│       ├── commands/        # lint, diff, export, spec CLI 서브커맨드
│       └── linter/
│           ├── parser/      # Markdown/YAML 파싱 레이어
│           ├── model/       # 토큰 해석 및 심볼 테이블
│           ├── linter/      # 규칙 엔진 + 10개 lint 규칙
│           ├── tailwind/    # Tailwind v3/v4 이미터
│           ├── dtcg/        # W3C DTCG 포맷 이미터
│           ├── fixer/       # 자동 수정 핸들러
│           └── spec-gen/    # spec.md 자동 생성기
├── PHILOSOPHY.md            # 포맷 철학 문서
├── CONTRIBUTING.md          # 기여 가이드 (Google CLA)
├── skills-lock.json         # 에이전트 스킬 잠금 파일
└── turbo.json               # Turborepo 파이프라인 설정

구조 평가: 기능 지향(function-oriented) 구조. 코드와 운영 자산이 명확히 분리됨. 현재 단일 패키지이나 모노레포 구조로 향후 확장 가능.

Step 3. 소프트웨어 스택

구분 기술
언어 TypeScript (strict, exactOptionalPropertyTypes, noUncheckedIndexedAccess, ES2022 target)
런타임/패키지 매니저 Bun 1.3.9 (고정 버전)
모노레포 도구 Turborepo (빌드/테스트/lint 파이프라인 오케스트레이션)
CLI 프레임워크 citty ^0.1.6
Markdown 파싱 unified + remark-parse + remark-frontmatter + unist-util-visit
YAML 파싱 yaml ^2.7.1
스키마 검증 zod ^3.24.0
빌드 bun build (번들링) + tsc (타입 선언 생성)
테스트 Bun 내장 테스트 러너
데이터 저장소 없음 (로컬 파일 처리)
배포 npm (wombat-dressing-room Google 프록시)
CI/CD GitHub Actions

Step 4. 아키텍처 분석

처리 파이프라인 (단방향 데이터 흐름):

입력 (DESIGN.md 문자열)
   │
   ▼
[ParserHandler]          ← remark + YAML 파싱, 프론트매터/코드블록 병합
   │ ParsedDesignSystem
   ▼
[ModelHandler]           ← 토큰 해석, 색상/치수 파싱, 레퍼런스 해석, 순환 감지
   │ DesignSystemState (Map 기반 심볼 테이블)
   ▼
   ├──[runLinter]        ← 10개 순수 함수 규칙 순차 실행 → Finding[]
   ├──[TailwindEmitter]  ← Tailwind v3 JSON 테마 생성
   ├──[TailwindV4Emitter]← Tailwind v4 CSS @theme 생성
   ├──[DtcgEmitter]      ← W3C DTCG tokens.json 생성
   └──[FixerHandler]     ← 섹션 순서 자동 수정

핵심 패턴: - Handler/Spec 패턴: 각 모듈은 handler.ts (구현) + spec.ts (타입/인터페이스) + handler.test.ts + spec.test.ts 4파일 구조 - 순수 함수 규칙 엔진: LintRule = (state: DesignSystemState) => Finding[] 시그니처로 각 규칙 독립 합성 가능 - Never-throw 설계: 파서와 모델 핸들러는 예외 대신 { success: true/false, data/error } Result 타입 반환 - 토큰 레퍼런스 해석: {colors.primary} 형식 교차 참조를 최대 깊이 10까지 해석, 순환 감지 포함

아키텍처 패턴: 파이프라인 + 포트/어댑터(각 이미터가 동일 DesignSystemState 입력 공유)

Step 5. 품질 및 테스트 시스템

테스트 구성: - 34개 테스트 파일, 소스 옆 배치(*.test.ts) - 규칙별 단위 테스트 (10개 lint 규칙 각각 독립 테스트) - fixtures/ 실제 DESIGN.md 파일 기반 통합 테스트 - fixture.test.ts + index.test.ts로 전체 파이프라인 검증 - W3C DTCG 적합성 테스트 (conformance.test.ts)

CI/CD (.github/workflows/test.yml): - Ubuntu: 의존성 설치 → lint (tsc --noEmit) → 단위 테스트 → 빌드 → Node.js 스모크 테스트 → tarball 스모크 테스트 - Windows: npm 레지스트리에서 @google/design.md@latest 직접 설치 후 스모크 테스트 - Bun 버전 고정 (1.3.9, packageManager 필드와 일치 검증)

정적 분석: TypeScript strict + exactOptionalPropertyTypes + noUncheckedIndexedAccess — 런타임 null 오류 사전 차단

커버리지 도구: 별도 커버리지 리포트 도구 미설정 (Bun 내장 커버리지 미활용)

강점 (Strengths)

  1. 철학이 코드에 직접 반영된 아키텍처: "Never-throw" Result 타입, 순수 함수 규칙 엔진, Handler/Spec 패턴이 PHILOSOPHY.md의 "prose over tokens" 사상과 대응하여 코드-문서 일관성 탁월
  2. 에이전트 우선(Agent-first) 설계: CLI JSON 출력, 프로그래매틱 API(@google/design.md/linter), .agents/skills/ 통합, spec 명령어(에이전트 프롬프트 컨텍스트 주입용)가 AI 워크플로 전반 커버
  3. 단방향 파이프라인의 높은 테스트 용이성: Parser → Model → Linter 각 레이어가 독립적으로 테스트 가능하며, 34개 테스트 파일이 규칙 단위로 격리되어 회귀 방지 우수
  4. 표준 상호운용성: DTCG(W3C), Tailwind v3/v4, {token.ref} 레퍼런스 문법이 기존 디자인 시스템 생태계와 통합 가능하게 설계
  5. 스펙 자동 생성 체계: spec-config.yaml 단일 진실의 원천 → bun run spec:gen → docs/spec.md 자동 동기화로 문서-코드 드리프트 방지

위험/개선 필요 사항 (Risks & Improvements)

  1. SECURITY.md 및 취약성 관리 부재: dependabot/renovate 미설정으로 remark, yaml 등 파싱 라이브러리 취약점 알림 체계 없음. Google 오픈소스 프로젝트임에도 OSS VRP 대상 제외로 외부 보안 보고 채널 불명확
  2. CHANGELOG 및 릴리스 노트 부재: v0.3.0까지 변경 이력 미추적. alpha 단계에서 breaking change 관리가 어려워 소비자에게 마이그레이션 부담 가중
  3. 테스트 커버리지 계측 미설정: Bun 내장 커버리지 (bun test --coverage) 미활용. 어떤 코드 경로가 미검증 상태인지 가시성 없음. 특히 model/handler.ts의 복잡한 레퍼런스 해석 로직
  4. 이슈/PR 템플릿 및 라벨 시스템 부재: .github/ISSUE_TEMPLATE/ 없음. 버그 리포트와 피처 요청 구조화 미비로 커뮤니티 기여 장벽 존재
  5. Alpha 포맷 불안정성: README가 "Expect changes to the format as it matures"를 명시. spec-config.yaml의 토큰 스키마가 외부 코드 생성기에 직접 영향을 미치므로 버전 관리 없는 alpha 변경은 생태계 채택을 저해할 수 있음

도입 권고 (Adoption Recommendation)

기술 도입 관점: 조건부 권고.

DESIGN.md 포맷과 CLI는 AI 에이전트 기반 프론트엔드 개발 워크플로에서 명확한 가치를 제공한다. 코드 아키텍처는 성숙도 이상으로 정교하며(Handler/Spec 패턴, 순수 함수 규칙 엔진, Never-throw 설계), 테스트 커버리지도 규칙 단위 격리 수준이 높다. Tailwind v3/v4 및 W3C DTCG 표준 지원으로 기존 디자인 시스템과 연계 가능하다.

그러나 alpha v0.3.0 상태로 포맷 안정성 보장이 없다. 프로덕션 디자인 시스템에 직접 통합하는 것보다 에이전트 프롬프트 컨텍스트 주입(spec 명령어)과 CI 검증 게이트(lint 명령어)로 제한적 도입을 권장한다. SECURITY.md 및 CHANGELOG가 갖춰지고 beta 태그가 붙는 시점에 전면 도입을 재검토할 것을 제안한다.

아키텍처 벤치마킹 관점: Handler/Spec 패턴과 단방향 파이프라인 설계는 유사한 마크다운 기반 DSL 파서/린터를 구현하는 팀에게 참조 아키텍처로 권고 가능하다.
