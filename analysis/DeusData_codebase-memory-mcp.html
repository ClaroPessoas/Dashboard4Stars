상세 분석

Step 1. 목적 및 범위

codebase-memory-mcp는 AI 코딩 에이전트(Claude Code, Codex CLI, Gemini CLI 등 11개)를 위한 MCP(Model Context Protocol) 서버다. 핵심 가치는 다음 두 가지다:

  1. 코드베이스를 지식 그래프로 변환: tree-sitter AST 분석으로 함수·클래스·임포트·호출체인을 그래프 노드/엣지로 추출하고 SQLite에 영속화.
  2. 에이전트 토큰 비용 절감: 파일별 Grep/Read 탐색 대비 99.2% 토큰 절감 주장(~412,000 → ~3,400 토큰). arXiv 논문으로 학술 검증.

타깃 사용자는 MCP 호환 AI 코딩 에이전트를 사용하는 개발자이며, 도구 성격은 정적 바이너리 MCP 서버 + CLI 도구다.

Step 4. 아키텍처 분석

진입점: src/main.c — 단일 main() 함수가 인수 파싱 후 MCP stdio 서버 또는 CLI 모드로 분기. 시그널 핸들러(SIGTERM/SIGINT), 부모 프로세스 watchdog 스레드, 배경 watcher 스레드를 초기화.

핵심 데이터 흐름:

파일 시스템 → discover(gitignore 계층) → pipeline(멀티패스)
    → pass_definitions.c  (함수·클래스·타입 노드 생성)
    → pass_calls.c        (호출 엣지 추출)
    → pass_lsp_cross.c    (Hybrid LSP 타입 해석 → RESOLVED_CALLS 정제)
    → pass_infrascan.c    (Dockerfile·K8s·Kustomize)
    → pass_similarity.c   (MinHash LSH 유사 코드 탐지)
    → pass_semantic.c     (Nomic 벡터 임베딩)
    → store(in-memory SQLite) → 완료 시 단일 덤프
    → watcher(배경 스레드, git 폴링) → 증분 재인덱싱
    → MCP 서버(14 도구 JSON-RPC 2.0) → 에이전트 클라이언트

Hybrid LSP 2레이어: - Layer 1: tree-sitter syntactic pass (158개 언어 전체) - Layer 2: 타입 인식 pass (Python·TS/JS·PHP·C#·Go·C/C++·Java·Kotlin·Rust 9개 언어)

Cypher 서브셋: src/cypher/cypher.c — 독자 구현 read-only openCypher 파서. MATCH·WHERE·WITH·RETURN·UNION 지원. SQLite SQL로 변환 실행.

아키텍처 패턴: 파이프라인 패턴(pass_*.c 각각 독립 패스). 계층 분리(foundation ↔ pipeline ↔ store ↔ mcp). 이벤트 기반은 아니며 순차적 인덱싱 + 배경 watcher 모델.

강점

  1. 산업 최고 수준의 릴리즈 보안 파이프라인 SLSA Level 3 증명 + Sigstore keyless 서명 + VirusTotal 72+ 엔진 + CodeQL SAST + OpenSSF Scorecard + SBOM을 모두 갖춘 오픈소스 도구는 극히 드물다. draft → verify → publish 패턴으로 중간 상태 배포를 원천 차단.

  2. 탁월한 테스트 심도와 범위 5,604개 케이스, 90+ 파일, 114K LOC의 테스트 코드. ASan+UBSan 빌드, 퍼즈 테스트, 4시간 주간 소크 테스트, 5개 플랫폼 CI. test_c_lsp.c 단일 파일만 15,930 LOC — 언어 지원 품질에 대한 진지한 투자.

  3. 공급망 최소화 및 완전 벤더링 모든 C 의존성이 소스 형태로 vendored되어 컴파일 타임에 정적 링크. 런타임 의존성 제로, 패키지 관리자 없음. 라이선스 게이트 CI 자동화로 라이선스 위반 즉시 차단.

  4. 아키텍처적 확장성 멀티패스 파이프라인(pass_*.c)이 각 독립 패스로 구성되어 새 언어·인프라 타입 추가 시 기존 코드 변경 최소화. CONTRIBUTING.md에 인프라 언어 추가 패턴이 상세히 문서화.

  5. 학술적 검증과 실용성의 결합 arXiv 논문(31개 저장소, 83% 품질, 10× 토큰 절감)으로 학술 검증을 갖추면서, 동시에 원라인 설치와 8개 패키지 매니저 배포를 통해 실용적 접근성 확보. docs/BENCHMARK.md에 63개 언어 상세 점수표 공개.

위험 / 개선 필요 사항

  1. 단일 유지관리자 리스크 (버스 팩터 = 1) SECURITY.md의 연락처(martin.vogel.tech@gmail.com)가 개인 이메일이며, 기여자 다양성이 확인되지 않는다. 프로젝트 규모(5,604 테스트, 158개 언어, 9개 Hybrid LSP)에 비해 지속성 리스크가 높다. GitHub Sponsors 또는 조직화 계획이 문서화되어 있지 않다.

  2. vendored C 라이브러리 자동 업데이트 부재 Dependabot이 GitHub Actions만 커버하고, vendored/의 C 라이브러리(SQLite, mimalloc, yyjson, TRE 등)는 수동 관리다. 이 라이브러리들에서 CVE가 발생해도 자동 알림이 없다. scripts/vendored-checksums.txt로 무결성은 검증하지만 버전 추적은 사람 의존.

  3. Nix flake 버전 불일치 flake.nix의 version = "0.6.0"이 현재 릴리즈 v0.8.1과 두 메이저 버전 차이. Nix 사용자는 잘못된 버전 메타데이터를 받는다. 릴리즈 파이프라인에서 flake.nix 버전 동기화가 누락된 것으로 보인다.

  4. graph-ui 테스트 범위 부족 graph-ui/는 React 19 + Three.js 3D 시각화이나 src/App.tsx 단일 파일 구조로 매우 초기적이다. package.json에 vitest 설정이 있으나 실제 테스트 파일이 확인되지 않는다. UI 컴포넌트 품질이 코어 C 엔진 대비 현저히 낮다.

  5. CHANGELOG 부재 및 버전 관리 인프라 일부 취약 공식 CHANGELOG.md가 없고 릴리즈 노트는 커밋 메시지 자동 생성에 의존. 과거 0.8.0 릴리즈 실패(pkg/npm 버전 미동기) 이력이 release.yml 주석에 기록되어 있으며, 버전 동기화 단계가 워크플로우에 사후 추가된 형태. 더 견고한 버전 관리 전략이 필요.
