상세 분석 / Detailed Analysis

1. 목적 및 범위 / Purpose and Scope

한국어: iptv-org/iptv는 전 세계 190여 개국의 공개 IPTV 스트림 URL을 국가별, 언어별, 카테고리별, 지역별로 분류하여 M3U 플레이리스트 형태로 제공하는 커뮤니티 기반 오픈소스 데이터 저장소이다. 직접 영상 파일을 저장하거나 재배포하지 않으며, 외부 저작권자가 공개적으로 제공하는 스트림 URL 포인터만 관리한다. VLC, Kodi 등 IPTV 플레이어 사용자와 IPTV 관련 서비스 개발자를 주요 대상으로 한다.

English: iptv-org/iptv is a community-driven open-source data repository that collects and classifies publicly available IPTV stream URLs from 190+ countries into M3U playlist format, organized by country, language, category, and geographic region. No video files are stored — only URL pointers to externally hosted streams. Primary audiences are IPTV player users (VLC, Kodi) and developers building IPTV-related services.

4. 아키텍처 분석 / Architecture Analysis

한국어: 전체 시스템은 이슈 기반 자동화 파이프라인 구조를 따른다.

  1. 데이터 수집: GitHub Issues를 입력 소스로 활용. update 워크플로우가 매일 00:00 UTC 실행 시 loadIssues()를 통해 Octokit GraphQL API로 labels:streams:add/edit/remove 이슈를 가져온다.

  2. 데이터 처리: Stream.updateWithIssue()가 이슈 메타데이터를 파싱하여 M3U 파일을 갱신. DataSet 클래스가 이슈 폼 필드를 파싱.

  3. 검증·린팅: playlist:validate가 채널 ID 유효성과 URL 형식을 검사, playlist:lint(m3u-linter)가 M3U 문법을 검사.

  4. 공개 플레이리스트 생성: 12개의 Generator 클래스가 내부 streams/*.m3u를 읽어 카테고리별, 국가별, 언어별, 지역별 공개 M3U 파일을 .gh-pages/에 생성.

  5. 배포: JamesIves/github-pages-deploy-action으로 gh-pages 브랜치에 배포, 별도 iptv-org/api 저장소에도 streams.json 푸시.

GitHub Issues
    ↓ (Octokit API)
playlist:update (Node.js/TypeScript)
    ↓
streams/*.m3u (internal)
    ↓ playlist:validate + playlist:lint
playlist:generate
    ↓
.gh-pages/ (public playlists)
    ↓ GitHub Pages Deploy Action
https://iptv-org.github.io/iptv/

English: The system follows an issue-driven automation pipeline pattern. GitHub Issues act as the input interface for community contributions. The Stream model extends @iptv-org/sdk's base model with IPTV-specific logic (filepath management, URL normalization, broadcast area resolution). Generator classes implement a uniform Generator interface and handle the fan-out from internal playlists to the many public playlist variants.

5. 품질 및 테스트 / Quality and Test System

한국어: - 테스트 방식: tests/commands/ 아래 9개 통합 테스트 파일. execSync로 실제 npm 스크립트를 실행한 뒤 출력 파일을 tests/__data__/expected/의 기대값과 파일 단위로 비교하는 실행 결과 스냅샷 방식. - 환경 격리: cross-env를 활용해 테스트용 경로(STREAMS_DIR, DATA_DIR, PUBLIC_DIR, LOGS_DIR)를 환경변수로 주입. TESTING=true 시 스트림 테스트 결과는 mock 파일에서 읽음. - 커버리지: Jest 커버리지 설정 없음. 단위 테스트 부재. - CI: check.yml은 PR 단위로 변경된 스트림 파일만 lint+validate. format.yml은 수동 실행. update.yml은 매일 스케줄 실행. - 린팅: ESLint (TypeScript 코드), m3u-linter (M3U 파일 문법), Prettier (스타일).

English: Tests are integration-level: each test launches a real subprocess and does file-diff comparison against fixture data. This provides high confidence in end-to-end behavior but makes unit-level regression harder to isolate. No coverage tooling is configured. The three CI workflows cleanly separate PR validation (check), manual formatting (format), and daily pipeline (update).

6. 보안 및 공급망 / Security and Supply Chain

한국어: - SECURITY.md: 없음 (부재). 보안 취약점 신고 절차가 문서화되어 있지 않음. - 의존성 관리: Dependabot 또는 Renovate 설정 파일 없음. 수동 업데이트 의존. - 라이선스: 프로젝트 자체는 Unlicense (퍼블릭 도메인). package.json에는 MIT라고 표기되어 일치하지 않음 (실제 LICENSE 파일은 Unlicense). - 비밀 관리: GitHub Secrets (APP_ID, APP_PRIVATE_KEY)로 GitHub App 토큰 관리. 코드에 시크릿 하드코딩 없음. - SBOM: 없음. - 공급망 위험: @freearhey/core, @freearhey/storage-js는 프로젝트 메인테이너 소유의 소규모 패키지로 외부 감사가 제한적. - 콘텐츠 위험: Xtream Codes 서버 URL 거부, 차단 목록(blocklist) 기반 채널 필터링, NSFW 필터(isSFW()) 내장. - 법적 보호: README에 DMCA 면책 조항 및 저작권 침해 신고 절차 명시.

English: The most notable security gap is the absence of a SECURITY.md and any automated dependency scanning. The project also has a package.json/LICENSE inconsistency (MIT vs Unlicense). The GitHub App token pattern for bot automation is a reasonable privilege-separation approach. Content safety is handled at the application level (blocklist, NSFW filter) rather than infrastructure level.

The project has extraordinary operational maturity for a data-driven repository: fully automated daily pipeline, bot-assisted issue processing, multi-destination deployment. Community activity is exceptionally high given 39,000+ merged PRs.

강점 / Strengths

  1. 완전 자동화된 데이터 파이프라인: GitHub Issues → 자동 M3U 업데이트 → 검증·린팅 → 공개 플레이리스트 생성 → GitHub Pages 배포가 매일 무인으로 실행됨. 사람의 개입 없이 커뮤니티 기여가 제품에 반영되는 수준의 자동화. (Fully automated data pipeline running daily without manual intervention.)

  2. 강력한 도메인 모델과 생태계 통합: @iptv-org/sdk로 채널·피드·방송 지역·언어·카테고리 등 복잡한 TV 방송 도메인을 SDK 수준으로 추상화. 별도 저장소(database, api, epg)와 일관된 SDK로 연동되는 마이크로서비스 생태계 구조. (Well-abstracted domain model via dedicated SDK, cleanly integrated with a multi-repo organization ecosystem.)

  3. 다차원 플레이리스트 생성: 단일 소스(streams/.m3u)에서 국가별, 언어별, 카테고리별, 지역별, 도시별, 서브디비전별 총 12종의 공개 플레이리스트를 자동 생성. Generator 패턴으로 쉽게 확장 가능. (Multi-dimensional playlist generation from a single source using an extensible Generator pattern.)*

  4. 기여 친화적 워크플로우: 5종 이슈 템플릿, 상세한 CONTRIBUTING.md, PR 검증 자동화(check.yml)로 39,000개 이상의 커뮤니티 PR을 효율적으로 처리. 기여 장벽이 매우 낮음. (Excellent contributor onboarding with templates, detailed guide, and automated PR validation that scales to 39k+ contributions.)

  5. 실용적 스트림 검증: mediainfo.js, HLS 파서, MPD 파서를 조합하여 URL 유효성뿐 아니라 실제 미디어 트랙 존재 여부까지 검증. 지오블로킹·타임아웃·HTTP 오류 코드를 세분화하여 정확한 상태 보고. (Practical stream health checking that validates actual media track presence beyond URL reachability.)

위험/개선 필요 사항 / Risks and Improvement Areas

  1. 보안 정책 부재 및 의존성 취약점 관리 미흡: SECURITY.md가 없어 취약점 신고 경로가 불명확. Dependabot이나 Renovate 없이 수동 의존성 업데이트. @freearhey/core 등 소규모 내부 패키지에 대한 공급망 감사 부재. (No SECURITY.md, no automated dependency scanning, and small internal packages with limited external audit trail.)

  2. 라이선스 불일치: LICENSE 파일은 Unlicense(퍼블릭 도메인)인데 package.json에는 MIT로 표기되어 있어 법적 혼선 가능성. (License mismatch between LICENSE file (Unlicense) and package.json (MIT) field.)

  3. 테스트 커버리지 및 단위 테스트 부재: 모든 테스트가 통합 수준의 subprocess 실행 방식이어서 개별 함수 레벨의 회귀 탐지가 어려움. 스트림 URL 정규화, 도메인 모델 메서드 등 핵심 로직에 단위 테스트 없음. (All tests are integration-level subprocess tests with no unit tests or coverage measurement, making fine-grained regression detection difficult.)

  4. 데이터 품질의 외부 의존성: 채널 메타데이터(이름, 카테고리, 로고 등)가 전적으로 외부 저장소(iptv-org/database)에 의존. 해당 저장소의 데이터 오류나 서비스 중단이 이 저장소의 플레이리스트 품질에 직접 영향. (Entire channel metadata quality depends on an external repository; any outage or data error in iptv-org/database propagates directly.)
