1. 목적 및 범위 (Step 1)

EN: container is a CLI tool developed by Apple that runs Linux containers as individual lightweight virtual machines on macOS (Apple silicon). Unlike Docker Desktop's shared-VM model, each container runs in its own VM using Apple's Virtualization framework, maximizing security isolation and per-container memory privacy. The tool is OCI-compatible — images can be pulled from/pushed to any standard registry and run in any OCI-compatible runtime.

KO: container는 Apple이 개발한 macOS용 Linux 컨테이너 실행 CLI 도구로, 각 컨테이너를 독립적인 경량 가상 머신(VM)으로 구동합니다. Docker Desktop의 공유 VM 방식과 달리 VM-per-container 설계를 채택하여 컨테이너 간 격리를 VM 수준으로 끌어올렸습니다. OCI 표준을 완전 준수하므로 기존 레지스트리 이미지를 그대로 사용할 수 있습니다.

  • 대상 사용자: macOS Apple silicon 사용자, 특히 Linux 컨테이너를 개발·테스트하는 백엔드 개발자
  • 프로젝트 유형: CLI 도구 + 시스템 데몬 + Swift 라이브러리 모음

아키텍처 패턴

사용자
  │
  ▼
[container CLI]
  │  XPC (ContainerXPC)
  ▼
[container-apiserver]  ←→  [container-core-images]  (OCI 이미지 관리)
  │  XPC                 XPC
  │                      
  ├──[container-network-vmnet]  (vmnet 가상 네트워크)
  │
  └──[container-runtime-linux] × N  (컨테이너당 1개, VM 생명주기 관리)
        │
        ▼
    [Linux VM per Container]  ← Apple Virtualization.framework
  • 통신 패턴: CLI ↔ 데몬 = XPC (Unix 도메인 소켓), 빌더 ↔ shim = gRPC over HTTP/2
  • 아키텍처 스타일: Plug-in 기반 마이크로서비스 아키텍처 (macOS 전용). Client/Server 이중 모듈 패턴.
  • 상태 관리: 파일시스템 기반 (ContainerPersistence) — 컨테이너, 볼륨, 네트워크 메타데이터를 TOML/JSON으로 디스크에 저장
  • 동시성 모델: Swift 6 strict concurrency — Sendable, actor, nonisolated(unsafe) 사용
  • VM-per-container: 핵심 설계 결정. 각 컨테이너는 독립 Virtualization.framework VM으로 실행 → 컨테이너 간 완전 격리

강점 (Strengths)

  1. VM-per-container 보안 격리: 각 컨테이너가 독립 VM으로 실행되어 컨테이너 탈출 공격 표면을 획기적으로 줄임. 기존 Docker Desktop 대비 근본적으로 다른 보안 모델.

  2. 완벽한 Swift 6 동시성 채택: Sendable, strict concurrency, actor 전면 적용. 데이터 레이스 버그를 컴파일 타임에 방지하는 최신 Swift 관용구 완전 준수.

  3. Client/Server 모듈 이중 분리 패턴: ContainerAPIClient/ContainerAPIService, ContainerNetworkClient/ContainerNetworkServer 등 모든 서비스가 클라이언트·서버 라이브러리로 분리되어 테스트 용이성과 재사용성 극대화.

  4. 공급망 보안 강화: GitHub Actions SHA 핀닝, GPG 커밋 서명 강제, hawkeye 라이선스 헤더 자동화 — CI 체인 전반에 걸쳐 변조 방지 조치 적용.

  5. 운영 문서의 완성도: README에서 기술 개요, 튜토리얼, API 문서, 버그 리포트 가이드까지 계층적으로 잘 구성된 문서 생태계. DocC 자동 게시로 API 문서 최신성 유지.

위험/개선 필요 사항 (Risks & Improvements)

  1. Swift 패키지 취약점 스캔 부재: Dependabot이 GitHub Actions만 커버하고 Swift 의존성(30개 이상)은 스캔하지 않음. swift package audit 또는 Snyk/OSV-Scanner 통합 필요. containerization exact 핀은 보안 패치 업스트림 적용을 차단.

  2. macOS 전용 플랫폼 잠금: Apple silicon + macOS 15/26만 지원. Linux/Windows 환경에서는 빌드·실행 불가. CI 러너도 self-hosted macOS ARM64 전용이므로 외부 기여자의 CI 접근이 제한적.

  3. SBOM·아티팩트 검증 없음: .pkg 배포물에 코드사이닝은 있으나 SBOM 생성, Sigstore/notarytool 외 독립적 아티팩트 서명, sha256 체크섬 게시가 없어 공급망 투명성이 부족.

  4. 0.x.x 안정성 한계: 마이너 버전 간 Breaking Change 허용 정책으로 라이브러리로서의 API 안정성 보장 없음. 프로덕션 환경 도입 시 버전 고정 필수. 1.0.0까지 유지보수 부담이 높음.

  5. 메모리 풍선 반환 미지원: Apple Virtualization.framework의 부분적 memory ballooning 구현으로 VM이 해제한 메모리를 호스트에 반환하지 못함. 메모리 집약적 다중 컨테이너 환경에서 호스트 메모리 고갈 위험. 상위 프레임워크 의존적 제한이나 문서화 필요.
