1. 목적 및 범위 (Purpose & Scope)

pytest는 Python 생태계의 사실상 표준 테스트 프레임워크(de facto standard)로, 2004년 Holger Krekel이 py.test로 시작하여 pytest-dev 조직이 유지한다. 단일 assert 문을 활용한 직관적 테스트 작성을 핵심 철학으로 하며 복잡한 기능 테스트에서도 확장 가능하도록 설계되어 있다.

주요 특징: - assert 문 재작성(AST rewriting)을 통한 풍부한 실패 메시지 - 자동 테스트 모듈·함수 검색(Auto-discovery) - 픽스처(fixture) 기반 모듈형 테스트 자원 관리 - unittest/trial 테스트 스위트 하위 호환 지원 - Python 3.10+, PyPy3 지원 - 1,300개 이상의 외부 플러그인 생태계

4. 아키텍처 분석 (Architecture Analysis)

핵심 패턴: 훅 구동 플러그인 시스템

pytest의 가장 독창적인 설계는 pluggy 기반의 훅 시스템이다.

hookspec.py (훅 명세 정의)
    ↓
_pytest/*/hookimpl (내장 플러그인이 훅 구현)
    ↑ ↑
사용자 플러그인 / conftest.py (훅 구현 추가)

내장 기능(터미널 리포터, JUnit XML, 캐시 프로바이더 등)이 모두 훅을 통해 구현되어 내부/외부 플러그인이 동등하게 취급된다. 1,300+ 외부 플러그인이 동일한 메커니즘으로 확장 가능하다.

실행 파이프라인

CLI (pytest / py.test)
    → _pytest.config:_console_main
    → Config 초기화 + PytestPluginManager
    → Session.main()
        ├── 수집(Collection): python.py, nodes.py
        ├── 실행(Execution): runner.py
        └── 보고(Reporting): terminal.py, reports.py, junitxml.py

특별 설계: AST 재작성 어서션 인트로스펙션

assertion/rewrite.py(47 KB)가 Python import hook을 통해 테스트 모듈 로딩 시 assert 문을 AST 변환하여 풍부한 진단 정보를 제공한다.

# 사용자 코드:
assert a == b

# 실패 시 자동 생성:
# E   assert [1, 2, 3] == [1, 2, 4]
# E   At index 2 diff: 3 != 4

픽스처 의존성 주입(DI) 시스템

fixtures.py(92.4 KB)가 함수 시그니처 인트로스펙션으로 의존성을 해석하고 스코프(function / class / module / package / session)에 따라 생명주기를 관리한다.

8. 강점 (Strengths)

  1. 독창적 훅 기반 플러그인 아키텍처: pluggy를 통해 내장 기능과 외부 플러그인이 동일한 메커니즘으로 동작하며 1,300개 이상의 플러그인 생태계를 가능하게 한다. 확장성과 일관성의 교과서적 설계.

  2. AST 재작성 기반 어서션 인트로스펙션: 추가 라이브러리 없이 표준 assert만으로 풍부한 실패 진단을 제공하는 기법. import hook을 활용한 pytest 최대의 기술적 차별점.

  3. 완전 자동화 릴리스 파이프라인 + SLSA 서명: GitHub OIDC attestation 기반 PyPI 아티팩트 서명, 자동 변경 이력 생성, git-tag 기반 버전 관리가 모두 자동화.

  4. 자기 참조적 테스트 전략: pytester로 pytest 자체를 격리 환경에서 블랙박스 테스트. 155개 파일, 45,000+ LOC, 28개 이상의 CI 매트릭스 조합으로 신뢰성 검증.

  5. 명확한 하위 호환성 정책 + Deprecation 관리: backwards-compatibility.rst 정책 명문화, Towncrier 10가지 변경 유형으로 체계적 이력 관리.

9. 위험 및 개선 필요 사항 (Risks & Areas for Improvement)

  1. 핵심 모듈의 복잡성 과부하: fixtures.py(92.4 KB), config/__init__.py(80 KB) 등 단일 파일이 지나치게 크다. 장기 유지보수 부담.

  2. Dependabot/자동 의존성 스캔 부재: 의존성 취약점 자동 탐지 체계가 미흡할 수 있어 공급망 보안 관점의 보완이 필요하다.

  3. SBOM 미생성: SLSA attestation은 적용되었으나 표준화된 SBOM(CycloneDX/SPDX)이 없어 엔터프라이즈 규정 준수 요구를 충족하기 어렵다.

  4. 픽스처 시스템 디버깅 난이도: DI 해석 + 스코프 관리 + 파이널라이저 체인이 강력하지만 문제 발생 시 추적이 어렵다. 전용 진단 도구가 필요하다.

  5. 다중 Python 버전 지원 누적 비용: 3.10~3.15 동시 지원으로 호환성 레이어가 누적되어 EOL 관리에 지속적 유지보수 비용이 발생한다.
