1. 프로젝트 개요 / Project Overview

1.1 목적 및 분류 / Purpose and Classification

  • 해결하는 문제 / Problem solved: LLM 애플리케이션에서 컨텍스트 토큰 과다 소비로 인한 비용 문제. 도구 출력, 로그, RAG 청크, 코드 파일, 대화 내역을 LLM에 전달하기 전에 60–95% 압축하여 API 비용을 절감하고 성능을 유지함.
  • 분류 / Classification: Platform (라이브러리 + 프록시 + MCP 서버의 복합 플랫폼)

Headroom is a practical AI infrastructure tool that serves as a multi-modal context compression library + drop-in proxy + MCP server.

  • Classification: Library + framework middleware + reverse proxy + MCP server (hybrid)
  • Real-world problems it solves:
  • Token cost explosion: AI agents repeatedly sending large tool outputs, logs, and files inflate token costs. Headroom compresses by 60–95% before they reach the LLM.

6. 성능 및 확장성 고려사항 / Performance & Scalability

[한국어]

알려진 성능 병목 지점:

  1. Kompress-base 모델 초기 로드: 첫 번째 압축 요청 시 HuggingFace 모델을 로드하며 수 초의 워밍업이 필요합니다. 프로덕션에서는 TRANSFORMERS_OFFLINE=1과 미리 캐시된 모델을 사용하십시오.
  2. AST 파싱 (CodeCompressor): 대형 코드 파일 처리 시 ast-grep 파싱이 일부 지연을 유발할 수 있습니다. transforms 기준 P99 < 50ms 목표.
  3. Neo4j 그래프 쿼리: 멀티-에이전트 메모리 시스템의 다중 홉 쿼리는 데이터 증가 시 느려질 수 있습니다. 프로덕션에서는 APOC 플러그인과 인덱스를 활용하십시오.
  4. PyPI 휠 크기: 릴리스 프로파일(strip + lto + codegen-units=1)로 휠 크기를 ~18MB → ~10MB로 최적화됨.

수평/수직 확장 전략: - 수평 확장: Headroom 프록시는 stateless로 설계되어 여러 인스턴스를 부하 분산 뒤에 실행 가능. CCR 저장소와 메모리 시스템은 외부 공유 스토리지(Qdrant 클러스터, Neo4j 클러스터)로 분리. - 수직 확장: ML 압축(Kompress-base)은 CPU 집약적. 인스턴스당 vCPU 증가가 가장 직접적인 효과. - 라이브러리 모드: 프록시 없이 인라인 사용 시 네트워크 오버헤드 없음 — 레이턴시 민감 앱에 적합.

캐싱 전략: - 프로바이더 KV 캐시: CacheAligner가 prefix 안정화로 캐시 히트율 극대화 (Anthropic cache_control, OpenAI prompt_cache_key 자동 삽입) - 압축 결과 캐시: headroom/cache/compression_cache.py가 동일 입력에 대한 재압축 방지 - HuggingFace 모델 캐시: ~/.cache/huggingface/ (로컬), CI는 GitHub Actions Cache 활용

Known performance bottlenecks:

  1. Kompress-base model initial load: On the first compression request, the HuggingFace model must load — expect a warm-up delay of several seconds. In production, use TRANSFORMERS_OFFLINE=1 with a pre-cached model.
  2. AST parsing (CodeCompressor): Processing large code files via ast-grep can introduce latency. Target: P99 < 50ms per transform.
  3. Neo4j graph queries: Multi-hop queries in the multi-agent memory system slow down as data grows. Use APOC plugins and indexes in production.
  4. PyPI wheel size: Release profile (strip + lto + codegen-units=1) reduces wheel size from ~18MB to ~10MB.

Horizontal / vertical scaling strategies: - Horizontal scaling: The Headroom proxy is stateless by design — run multiple instances behind a load balancer. Separate the CCR store and memory system into external shared storage (Qdrant cluster, Neo4j cluster). - Vertical scaling: ML compression (Kompress-base) is CPU-intensive — increasing vCPUs per instance is the most direct improvement. - Library mode: Inline use without the proxy has zero network overhead — ideal for latency-sensitive applications.

Caching strategies: - Provider KV cache: CacheAligner maximizes cache hit rates by stabilizing prefixes (auto-inserts Anthropic cache_control and OpenAI prompt_cache_key) - Compression result cache: headroom/cache/compression_cache.py prevents re-compressing identical inputs - HuggingFace model cache: ~/.cache/huggingface/ (local), CI uses GitHub Actions Cache
