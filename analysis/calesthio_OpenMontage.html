Step 1. 목적 및 범위 / Purpose and Scope

OpenMontage는 세계 최초의 오픈소스 에이전틱 비디오 프로덕션 시스템을 표방한다. 핵심 아이디어는 Python 코드가 아닌 LLM 에이전트(Claude Code, Cursor, Copilot 등)가 오케스트레이터 역할을 맡는다는 것이다. 사용자는 자연어로 "Make a 60-second explainer about black holes"와 같이 의도를 설명하고, 에이전트가 파이프라인 매니페스트(YAML)와 스테이지 디렉터 스킬(Markdown)을 읽어 전체 비디오 제작 워크플로우를 실행한다.

대상 사용자: AI 코딩 어시스턴트를 IDE에서 사용하는 콘텐츠 크리에이터, 개발자, 기업 홍보 담당자.
유형: 에이전틱 플랫폼 / 오픈소스 프레임워크.

OpenMontage is an instruction-driven video production system. The AI agent IS
the intelligence — it reads pipeline manifests (YAML) + stage director skills (MD)
and drives the pipeline using Python tools as building blocks.

Step 4. 아키텍처 분석 / Architecture Analysis

핵심 철학: 에이전트 퍼스트 오케스트레이션

Python = 도구 + 영속성
LLM 에이전트 = 창의적 결정 + 오케스트레이션 로직 + 리뷰 + 체크포인트 정책

Python에는 오케스트레이션 로직, 창의적 결정, 리뷰 로직, 체크포인트 정책이 없다. 에이전트가 Markdown 스킬과 YAML 매니페스트를 읽어 모든 결정을 내린다.

3계층 지식 아키텍처

Layer 3: .agents/skills/       외부 기술 지식 (47개 스킬)
         "기술이 어떻게 작동하는가"   FFmpeg, ElevenLabs API, FLUX, Remotion, GSAP 등
              ↑  agent_skills[] 참조
Layer 2: skills/               OpenMontage 전용 규약
         "이 프로젝트에서 기술을     파이프라인 통합, 품질 체크리스트, 아티팩트 매핑
          어떻게 쓰는가"
              ↑  스테이지 스킬 참조

         "무엇이 존재하고 언제 쓰는가"  BaseTool 계약, 파이프라인 매니페스트

파이프라인 상태 머신

12개 파이프라인이 각각 고유한 스테이지 진행을 갖지만, 대부분이 다음 표준 흐름을 따른다:

research → proposal → script → scene_plan → assets → edit → compose → publish

각 스테이지: 1. 스테이지 디렉터 스킬(MD) 존재 — 에이전트가 읽어야 하는 지시사항 2. tools_available 선언 — 에이전트가 호출할 수 있는 도구 3. 정규 아티팩트(JSON) 생성 — JSON Schema로 검증 4. review_focus + success_criteria 정의 5. 인간 승인 게이트(human_approval_default) 설정 가능

BaseTool 계약

모든 도구는 BaseTool(ABC)을 상속하며 필수 필드를 선언한다:

name, version, tier, capability, provider, runtime, stability,
dependencies, input_schema, output_schema, fallback_tools,
agent_skills, resource_profile, retry_policy

execute(inputs) → ToolResult 만이 유일한 필수 메서드.
ToolResult: success, data, artifacts, error, cost_usd, duration_seconds, seed, model.

셀렉터 패턴

세 셀렉터 도구가 멀티 프로바이더 능력을 추상화한다:

셀렉터 능력 패밀리 탐색 방법
tts_selector TTS registry.get_by_capability("tts")
image_selector 이미지 생성 registry.get_by_capability("image_generation")
video_selector 비디오 생성 registry.get_by_capability("video_generation")

셀렉터는 사용자 설정 > 가용성 > 탐색 순서로 라우팅하며 입력 스키마를 프로바이더 간에 투명하게 변환한다.

체크포인트 시스템

{
  "version": "1.0",
  "project_id": "my-video",
  "stage": "script",
  "status": "completed",
  "timestamp": "...",
  "checkpoint_policy": "guided",
  "artifacts": { "script": { ... } },
  "cost_snapshot": { ... }
}

상태: pending | in_progress | awaiting_human | completed | failed.
체크포인트 정책: guided (창의적 스테이지 승인) | manual_all | auto_noncreative.

render_runtime은 proposal 스테이지에서 잠기며, 이후 silent 교체는 금지된다.

강점 / Strengths

  1. 독창적 아키텍처 철학: "Python은 도구와 영속성만, 지능은 에이전트가" 원칙이 일관되게 적용된다. 이는 시스템을 특정 LLM에 종속시키지 않으면서도 에이전트의 품질에 따라 산출물이 자연스럽게 향상되는 구조를 만든다. 아키텍처 결정이 docs/ARCHITECTURE.md와 AGENT_GUIDE.md에 잘 문서화되어 있다.

  2. 셀렉터 패턴을 통한 우아한 프로바이더 추상화: tts_selector, image_selector, video_selector는 레지스트리에서 능력을 자동 탐색해 라우팅한다. 새 프로바이더 도구를 추가하면 셀렉터 코드 수정 없이 자동으로 사용 가능해진다. 이는 외부 API 20+를 관리하는 시스템에서 특히 가치 있는 설계다.

  3. 체계적인 예산 거버넌스: estimate→reserve→reconcile 생명주기, 단일 액션 승인 임계값, 유료 도구 첫 사용 확인 등이 CostTracker에 구현되어 있다. 비용이 발생하는 AI API를 다수 사용하는 시스템에서 이는 사용자 신뢰의 핵심이다.

  4. JSON Schema 기반 아티팩트 검증: 20개의 아티팩트 스키마가 모든 스테이지 출력을 검증한다. 잘못된 데이터가 파이프라인을 통해 전파되는 "garbage propagation"을 방지하는 계약 중심 설계다.

  5. 포괄적인 도구 생태계: 분석, 오디오, 아바타, 향상, 그래픽, 자막, 비디오 전반에 걸쳐 90개 이상의 도구. 클라우드 API와 로컬 GPU 모델을 모두 지원하는 이중 프로바이더 원칙이 일관되게 적용된다. 재고 미디어 소스도 18개 이상(NASA, ESA, JAXA, Wikipedia Commons, Pexels, Pixabay 등)이다.

위험/개선 필요 사항 / Risks and Areas for Improvement

  1. CI/CD 완전 부재: .github/workflows/가 없다. PR 병합 전 자동 계약 테스트가 실행되지 않는다. PR #57(외부 기여자)이 계약 테스트 없이 병합되었을 가능성이 있다. 최소한 pytest tests/contracts/를 실행하는 GitHub Actions 워크플로우가 필요하다.

  2. 보안 관리 체계 부재: SECURITY.md 없음, Dependabot/Renovate 없음, SBOM 없음. FFmpeg subprocess 호출 시 사용자 제공 파일 경로가 shell injection으로 이어질 수 있는 벡터가 있다. requests 기반 API 호출에서 응답 데이터 검증 수준도 도구마다 상이하다.

  3. AGPLv3 라이선스 + Remotion 라이선스 복합 위험: AGPLv3는 네트워크 서비스 배포 시 소스 공개 의무를 발생시킨다. Remotion은 별도의 상업 라이선스가 필요하다. 이 두 가지를 인식하지 못한 기업 사용자가 서비스에 임베드할 경우 법적 위험이 있다. README에 명시적 라이선스 경고가 없다.

  4. 단일 기여자 집중도: 전체 코드베이스가 사실상 단일 기여자(calesthio)에 의해 유지된다. CONTRIBUTING.md, 이슈 템플릿, PR 템플릿 없음. 외부 기여 온보딩 경로가 없어 커뮤니티 성장을 저해할 수 있다.

  5. 에이전트 런타임 의존성 취약점: 시스템의 지능이 에이전트 스킬(MD)에 있어 Python 테스트로는 품질 회귀를 잡기 어렵다. LLM이 AGENT_GUIDE.md를 읽지 않거나 잘못 해석하면 시스템 전체가 오작동한다. 에이전트 거버넌스 계약(Rule Zero, Decision Communication Contract 등)의 준수를 자동 검증할 방법이 없다.
